# Audit 3-work-items — Work items: ownership, area pointer, process, reads

As-is auditor, read-only. Facts checked against the code at doc/012 (2b4ba8aa); spec ids are cited where the code cites them. Paths are repository-relative under `src/backend/` unless a `docs/` prefix is shown. No iteration or sprint code exists anywhere in `src/backend` (grep): mod-007 and doc-004 are specs only.

## As-is (what exists, with repository-relative file paths and line numbers where it matters)

**What a work item belongs to**
- `Mustask.Domain/WorkItems/WorkItem.cs` L51-86: `Id` (v7), `ProjectId` (L53, never changes, BR-M3-2), `Number`, `TypeId`, `StateId`, `AssigneeId` (Keycloak sub, no FK, L63), `AreaId` (L65, required), `ParentId`, creation key, `ChangedAt`, feat-022 fields. There is no organization column, no team column and no sprint/iteration pointer. The tenant is derived: item → project → `projects.organization_id`.
- The team is not stored on the item. It is derived on every read as the resolved owner of the item's area: `AreaTree.ResolveOwner` (`Mustask.Domain/Organizations/AreaTree.cs`; explicit owner, else nearest owned ancestor, root owned by the project's first team, mod-002 BR-M1-11). `Mustask.Infrastructure/Boards/BacklogMembership.cs` L45 (`TeamAreas`) and L57 (`Members`): an item is on team T's backlog and board iff project matches, type is of the level, `area_id` is in T's area set, state is not Removed. So an item is on exactly one team's surfaces (doc-001 BR-3).
- Team and Area are project-scoped tables: `teams.project_id`, `areas.project_id`; `AreaConfiguration.cs` uses composite keys `(project_id, parent_id | owner_team_id | default_of_team_id)` onto `(project_id, id)`, one root per project (partial unique index), and the team's default area is a unique column on the area (`default_of_team_id`).
- Ownership therefore moves without any write to the item: re-owning or moving an area, deleting a team (its areas pass to the first team, BR-M1-18, BR-M4-20) or saving the item's «Область». The first three leave `ChangedAt` alone; the item arrives unplaced on the new backlog (BR-M4-6). Proved by `GetBacklogEndpointTests` (`Get_AreaReOwned_TakesItsItemsAlong`, `Get_AreaMoved_…`, `Get_DeletedTeam_ItsItemsGoToTheFirstTeamByNumber`, `Get_AreaSetOnTheForm_MovesTheItemToTheOtherTeam`).
- Backlog order is a separate row per item: `backlog_places` keyed by `work_item_id` alone, with a composite FK `(team_id, backlog_level_id)` to the backlog order (`BacklogPlaceConfiguration.cs`; the only Cascade out of `work_items`). One place per item, valid only while the item stays on that team's backlog (BR-M4-26 `reorder_stale`).

**The area pointer (how it is set and validated)**
- Create (`Mustask.Application/Features/WorkItems/CreateWorkItem/CreateWorkItemHandler.cs` L125-164): the project's root area (`ProjectInfo.RootAreaId`); else the body's `teamId` → `WorkItemRepository.LockTeamDefaultAreaAsync` (`Mustask.Infrastructure/WorkItems/WorkItemRepository.cs` L41-53: `teams WHERE id AND project_id FOR SHARE`, Active only, default = `areas.default_of_team_id`), unknown/foreign/deleted team → 404 `organizations.team.not_found`; a `parentId` wins over both (`WorkItemHierarchy.CreateChild` copies `parent.AreaId`, feat-027 BR-T-10).
- Save (`SaveWorkItemHandler.cs` L114, L192-210): unparsable id → 404 `organizations.area.not_found`; equal to the current area → no lock; otherwise `LockAreaAsync` (`WorkItemRepository.cs` L71-79: `areas WHERE id AND project_id FOR SHARE`, then re-read) → 404 if absent or of another project. The domain does not re-check it (`WorkItem.Save` L303-307; contract on `WorkItemEdit` L564-566).
- DB backstop: composite FK `(project_id, area_id)` → `areas(project_id, id)`, Restrict (`WorkItemConfiguration.cs` L83-88), so an area that holds an item cannot be deleted. mod-002's delete asks `IAreaUsage` (`WorkItemAreaUsage.cs`: any item of the project in the area, any state; race via FOR SHARE vs FOR UPDATE, BR-M3-24).
- Display: each list page and each item read loads the project's whole area tree and renders the path «A / B» (`WorkItemReadModel.AreaPathsAsync` L286-295).

**Process, states, transitions: whose process**
- One process per organization: `processes.organization_id` unique (`Mustask.Infrastructure/Process/Configurations/ProcessDefinitionConfiguration.cs`; mod-001 BR-M2-1; mod-002 BR-M1-3 "every project of the organization uses that process"). Handlers read it by the address's organization (`processes.FindByOrganizationAsync(organizationId)`; create L111-115, save L92-108); a type outside it answers 404 `workitems.workitem.type_not_found` (`Create_TypeNotOfTheOrganizationsProcess_…`).
- The database knows only `type_id → work_item_types` and `state_id → state_definitions` (Restrict). "The type belongs to the project's organization's process" and "the state belongs to the item's type" are handler/domain rules, not constraints (`WorkItemTypeStates.Allows`, `Mustask.Domain/WorkItems/WorkItemTypeStates.cs` L49).
- There is no transition model. A save may put the item in any state of its own type except the Removed category, from any state, no reason, no rule (BR-M3-21; `WorkItem.cs` L267-270; `Mustask.Domain/Process` has no transition entity). The type never changes (BR-M3-1).
- Board columns are derived on read from the organization's process per backlog level (`BoardLayout.Derive` in `GetBoardHandler.cs`); a column is headed by the state's name (bug-004 D-3) and `StateNameRule` keeps one category per state name inside a process. doc-007's release-3 editor is analysis only: it mutates the one process in place, no fork (P-3), never narrows any-to-any (BR-M2-7).

**Reads that exist (route, narrowing today)** — every one is narrowed by: the role of the caller's membership in the address's organization holding the route's code (ADR-0027; non-member → 404 `organizations.organization.not_found`); then `FindProjectAsync` + `project.OrganizationId == address org` + `IsReachable` (project and organization active) else 404 `organizations.project.not_found`; then `project_id` in SQL. Nothing narrows by area, team, project membership or item.
- List `GET …/projects/{p}/workitems?page=` (`WorkItemEndpoints.cs` L36, `GetWorkItemsHandler`, `WorkItemReadModel.GetPageAsync` L102-147): every item of the project in every state, `ChangedAt` desc then number desc, 50 a page (`WorkItemLimits.ListPageSize`), no filter, search or sort (BR-M3-29; feat-003 unbuilt). `count` (L107) is the project's unfiltered item count.
- One item `GET …/workitems/{identifier}` (`GetWorkItemHandler`): `(project, number)` and the type key must match the identifier (BR-M3-5); the answer carries the parent (any state) and the live children as refs (`LinksAsync` L207-227), the area path and the assignee with `isMember` (`ProjectMembers.MemberIdsAsync`).
- Parent candidates `GET …/{identifier}/parent-candidates` (`FindParentCandidatesAsync` L52-100): same project only, types allowed by level rank, state not Removed, title (ICU collation) or identifier text, limit 20 (`ParentCandidatesShown`) plus a more-matched flag.
- Assignee candidates `GET /api/organizations/{o}/workitems/assignee-candidates` (`GetAssigneeCandidatesHandler`): organization-level, code `workitems.workitem.write` (a viewer gets 403), active members of the organization found in the directory, at least 2 characters, at most 20; independent of project and team (doc-001 BR-13).
- Team backlog and board (mod-006, `Mustask.Api/Features/Boards/BoardEndpoints.cs`): addressed `…/projects/{p}/teams/{t}/backlogs|boards/{level}`; the handler requires `team.ProjectId == projectId` (`GetBoardHandler.cs` L42-48); the whole backlog is read, no paging (5 000 items in the volume tests); `ReadChecklistsAsync` reads children by project and parent, not by team (feat-032 BR-C-1).
- Counters: the list `count`; card checklist counters from the checklist children (feat-032 BR-C-2); `work_item_counters` is the number sequence, not a statistic. No per-area, per-team or per-status aggregate, no search endpoint and no cross-project read exist.
- Internals: `IWorkItemReadModel.GetAsync(Guid)` / `GetRefAsync(Guid)` filter by item id only (the caller "knows it exists"); every repository lock (`LockAsync`, `LockAreaAsync`, `LockTeamDefaultAreaAsync`, `LockNumberSequenceAsync`, `LockHierarchyAsync`) filters by `project_id`, not organization. The organization is enforced once per handler: the same project chain is repeated in six work-item handlers and three board handlers.
- The frontend reads an item only through the page's project: `src/frontend/src/features/workitems/components/WorkItemCardDialog.tsx` L101 `useWorkItem(organizationId, projectId, identifier)`; the card dialog is opened by `?workitem=<identifier>` on backlog and board rows.

**Links and hierarchy**
- Only parent/child (feat-001): column `parent_id`, composite FK `(project_id, parent_id)` so a parent is always of the same project; not-self check; parent rank >= child rank (BR-H-2); cycle and depth <= 64 (`WorkItemHierarchy.MaxChainLength`) decided under a per-project lock (`work_item_hierarchy_locks`, `LockHierarchyAsync`); an item in «Удалена» cannot be linked (BR-H-8). No cross-project link and no second link kind (feat-030 queued).
- A parent and its child may sit in areas of different teams: the child stands beneath no row of the other team's backlog (BR-T-4, `Get_AnotherTeamsChildren_StandBeneathNoRow`) but is in the parent's board checklist (`Get_ChildOfAnotherTeam_IsInTheChecklist_…`).

## Responsibilities the current model carries (one duty per bullet; mark where one entity carries several duties)

- Project membership and number sequence of the item: `ProjectId`, `work_item_counters`, identifier by project key (BR-M3-5). Single duty, stable.
- Classification / location shown to the user: the «Область» path on list, form, backlog. **Area carries this**.
- Team ownership of the item: derived from the area's owner. **Area carries this too** (one pointer, two duties; no explicit team on the item).
- Backlog and board membership: a function of the ownership above (BR-M4-5). **Area, via ownership**.
- Default placement at creation: a team's default area, or the parent's area. **Area + team default + hierarchy** are coupled here (BR-M3-20, BR-M1-14, BR-T-10).
- Deletion pin: an area holding any item is undeletable (BR-M3-24). **Area carries this as a side effect of the FK and `IAreaUsage`**.
- Access control: none. Neither area, team nor project narrows reads (org role bundle only; team membership grants no code, ADR-0027 rule 2; BR-5 "no finer than the organization"). This answers the brief § 2 question for work items: the area is not an authorization mechanism today.
- Assignee: any active organization member, independent of the owning team (BR-M1-26) — already decoupled from ownership.
- Process binding: type (immutable) → the organization's one process → states and board columns. No per-project or per-team process.
- Planning pointer: none exists on the item.
- Hierarchy: same-project parent/child; couples to ownership only at create (child inherits the parent's area).

## Rules and contracts the matrix model touches (by id) — for each: what in the brief collides

- BR-M3-2 (docs/features/mod-003-work-item-core/spec.md): an item's «Область» is an area of its own project, project fixed. Brief §§ 3.2, 4, 6.8: areas are organization-level and linked M:N to projects; the brief gives the item `ProjectId` and `OwningTeamId` but names no area pointer; whether the item keeps a classification pointer is undecided (brief § 13 only mentions "area paths used for classification").
- BR-M3-20 / mod-002 BR-M1-14 / mod-006 BR-M4-21 / feat-027 BR-T-10: default area at creation (root, team default, parent's area). Brief § 6 plus the human's decision: a project default team (settings, or the single linked team); a child's team is not specified.
- BR-M3-21 (any state to any state), doc-001 BR-10, doc-007 BR-M2-7: no workflow. Brief SC-10: "transitions validated by the source project's workflow", differing status sets per project, normalized categories. Today there is one process per organization, so SC-10 cannot occur; it requires a decision on process scope.
- mod-001 BR-M2-1, mod-002 BR-M1-3, doc-007 § Release 3 (P-3, in-place mutation): one process per organization, every project uses it. Brief § 7 and SC-10 imply per-project (or per-team) workflows.
- BR-M3-22, mod-016 BR-M1-26, doc-001 BR-13: assignee = any active organization member. Brief § 6: no team-membership rule; § 10: assignment "governed by access rights". Collision: a Restricted project's item may be assigned to someone who cannot read it.
- BR-M3-23 / BR-M3-24 / mod-002 BR-M1-13 (`IAreaUsage(projectId, areaId)`): area deletion guarded by items. Brief § 3.2/§ 12: deleting or unlinking an area never deletes or blocks projects, teams or tasks; the guard's meaning changes once items carry no area FK.
- BR-M3-27 / BR-M3-29, mod-003 api-contract § 0.1, § 2.1: reads narrowed by organization only; the list is the whole project. Brief §§ 7, 10.3, 10.4: every read, filter and counter respects project visibility; Restricted projects are not disclosed through counters, search or autocomplete; list needs filters (project, team, assignee, type, status, priority, sprint, date, blockers).
- ADR-0027 rules 1-3 and mod-016 BR-M1-33, api-contract § 4.2 rows 28-37: one organization code per route, role from membership, nested ids resolved from the outside in (organization, project, team/area in project, item in project), a non-member gets 404. Brief § 10: scoped permissions (organization, area, project, team) as an extension of this model (prior-art P-5).
- doc-001 BR-5: "MVP scopes no finer than the organization (no per-project or per-team override)". Brief § 10.3 Restricted needs exactly that override.
- doc-001 BR-3 / mod-006 BR-M4-5, BR-M4-20: an item is on exactly one team's surfaces via area ownership; a deleted team's items go to the first team. Brief §§ 6, 7.3: explicit `OwningTeamId`, optional (no team allowed), team board across projects (prior-art P-2). BR-M4-20 and the "first team" fall away if teams are organization-level.
- mod-006 BR-M4-6, BR-M4-26, `backlog_places` (one place per item): item changes team → unplaced. Brief § 6.10 / SC-09: sprint and ownership must stay consistent when the owner changes.
- mod-002 BR-M1-9, BR-M1-11, BR-M1-14, BR-M1-18, BR-M1-22 (first team, immutable root area, team default area, team deletion, no cross-project move): the machinery that derives item ownership today (prior-art P-1: retire or replace each by name). Brief § 5: teams are organization-level.
- feat-001 BR-H-1 (same-project links, composite FK), BR-H-2, BR-H-8; feat-032 BR-C-1: brief § 6 keeps "existing mechanisms of links" and adds sub-tasks with their own responsible teams; the checklist already crosses teams inside a project. Cross-project links are not asked for and do not exist.
- doc-004 BR-M5-1 (iteration belongs to one project), BR-M5-5 (team selects iterations), BR-M5-7 (pointer needs an iteration of the item's project selected by the item's area-owner team), BR-M5-12, BR-M5-16 and doc-001 BR-7: brief § 8 makes the sprint a team's, spanning projects, with item-sprint-team consistency; BR-M5-7 is the mirror image of brief § 6.10 and is built on area ownership.
- BR-M3-5 / mod-003 D-5 (address `…/projects/{p}/workitems/{identifier}`): brief §§ 7.3, SC-01 show items of several projects on one board; each card needs its own project in the address (frontend `WorkItemCardDialog.tsx` L101 reads in the page's project; the feat-028 queue note already flags it).
- BR-M3-25, BR-M3-28 and ADR-0010/0011 (item `FOR UPDATE`, parent and area locks, no concurrency token): owning team and sprint become item fields saved with the form; lock order with project/team link rows is new. `ChangedAt` semantics for ownership changes (today implicit changes do not move it).
- ADR-0026 rules 3 and 8 (reachability by containment; a write beneath reads only the container's status): team reachability is team+project+organization today (`Reachability.ReachableTeams`); an organization-level team has a different chain.
- ADR-0014 / ADR-0015 (paging envelope, Gridify for list queries): brief §§ 7, 14 server-side paging and filters; the list does not use Gridify filters yet and the backlog has no paging.
- Brief §§ 12, 21.8: no work-item copies for boards; satisfied today (one `work_items` table, no copies).

## Risks and open questions for the analyst

- Does the item keep any area or classification pointer, or only project, owning team and (later) sprint? If it keeps one, which of its four duties (display, ownership, membership, deletion pin) does it carry?
- Existing implicit-ownership tests (`GetBacklogEndpointTests` L236-L331) encode "area edit / re-own / team deletion moves items". Which survive, which are retired by name (P-1, P-2)?
- What does a team's backlog and board hold when a team spans projects: all items with `OwningTeamId = T` visible to the user; what order, and is `backlog_places` still keyed by item alone (one place) when the same item could be shown on several team views?
- A child created under a parent: does it inherit the parent's team (today it inherits the parent's area), the project default team, or none? Same for the human's default-team rule when the project has several linked teams and none is set.
- Process scope for SC-10: per organization (today, one process, so a project's "own" statuses do not exist), per project, or per team? Where do normalized categories (already one per state name in a process) stand across processes?
- Restricted-project answer: 404 or 403 for list, item, parent candidates, board? Today a project outside the organization is a 404 from the outside in; ADR-0027 gives a non-member 404.
- Per-surface visibility, named (P-4): list, item, refs/children, parent candidates, assignee candidates, backlog, board, checklists, list `count`, checklist counters, the area-deletion guard, and any new area/team/project board or search. Today none has a project-level filter, so each is a new predicate, in one shared policy.
- Tenant boundary (P-3): repository locks and by-id reads filter by `project_id` only. With organization-level teams and areas, which locks and reads need an organization predicate, and where is it enforced once?
- Unlinking a team from a project (SC-09, P-7) while it owns items: the model has no precedent; deleting a team today silently re-owns by area. Items, their sprints, `backlog_places` and the project default team all need a stated outcome.
- Cross-project cards: the item address is project-nested and identifiers resolve by project key inside the organization; a team board needs a per-card project in the route and the frontend's card dialog (page project) changes.
- Assignee vs access: keep "any active organization member" (BR-M1-26) or require read access to the item's project? The assignee candidates route is organization-level and has no project context.
- Sprint pointer: the item has none today and mod-007 is unbuilt; the owning-team match (brief § 6.10, P-8) is a new invariant that needs a lock order beside the item and team-link rows (ADR-0011).
- Contracts that change with no owner note yet (P-10): mod-003 api-contract §§ 1.1 (`area`), 2.1-2.4, 7; mod-006 api-contract §§ 1, 3, 7 (`teamId`); mod-016 api-contract § 4.2 rows 28-37; error codes `organizations.team.not_found`, `organizations.area.not_found` used by work-item routes.
- Volume: the backlog reads everything with no paging and the list loads the project's whole area tree per page; brief § 7 asks for paging or virtualization and an index plan on `(owning_team_id, …)` (existing indexes are all `project_id`-led).
