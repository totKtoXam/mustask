# Audit 2-access — Access and authorization: membership, roles, permission codes

Read-only audit of branch `doc/012-matrix-organization-model` (HEAD 2b4ba8aa). mod-016 is merged; feat-028 (org-level teams) is not: `Team` still has `ProjectId` (`src/backend/Mustask.Domain/Organizations/Team.cs:30`). Paths are repository-relative.

## As-is (what exists, with repository-relative file paths and line numbers where it matters)

**A request, end to end (backend).**
- Authentication: Keycloak JWT; `KeycloakPermissionClaims.Append` copies only `resource_access.mustask-api.roles` into claims `perm` (`Mustask.Api/Authentication/KeycloakPermissionClaims.cs:26-60`); realm roles and groups are never read. The fallback policy denies everything not declared (`JwtBearerSetup.cs:115-118`).
- A route declares exactly one of four categories (`Mustask.Api/Authorization/EndpointCategories.cs`): `RequiresPermission(instanceCode)` -> policy `perm:<code>` = a claim check (`PermissionPolicies.cs:42-51`); `RequiresOrganizationPermission(orgCode, acceptsDeactivated)` -> policy `org:` / `org+restore:` with `OrganizationPermissionRequirement(Code, AcceptsDeactivated)` (`PermissionPolicies.cs:53-76`); `AuthenticatedOnly(reason)`; `Public(reason)`. A code of the wrong scope throws at mapping time (`EndpointCategories.cs:56-66`).
- The scoped check is an authorization handler, so it runs before the body is bound (`OrganizationPermissionHandler.cs:37-83`). It reads one route value, `organizationId` (:47), parses it (:49), runs one statement joining organization status to the caller's role (`Mustask.Infrastructure/Organizations/OrganizationAccessReadModel.cs:14-24`), and fails with one reason for a missing, malformed, inactive (restore excepted) or non-member organization (:58-71). If the role bundle lacks the code it fails with another (:73). On success it keeps `ResolvedOrganizationAccess(OrganizationId, Role)` in `HttpContext.Items` (:81). `ForbiddenErrorCodeResultHandler.cs:32-44` renders the two reasons as 404 `organizations.organization.not_found` and 403 `organizations.access.forbidden`.
- Below that, no code looks at a project, team or area for access. Each handler resolves nested ids itself, outside in; nine Boards/WorkItems handlers repeat `FindProjectAsync(...)` plus `project.OrganizationId != organizationId` (e.g. `Features/Boards/GetBacklog/GetBacklogHandler.cs:41`, `Features/WorkItems/GetWorkItems/GetWorkItemsHandler.cs:33`). `IOrganizationStructure` (the reads other modules use) takes no caller (`Infrastructure/Organizations/OrganizationStructure.cs:84-167`).
- Second codes and re-checks use the resolved role only: `IOrganizationAccess.Holds` (`HttpContextOrganizationAccess.cs:22`) at `CreateWorkItemHandler.cs:71` and `SaveWorkItemHandler.cs:65` (parent needs `workitems.link.write`); the actor role is re-read under the lock at `ChangeMemberRoleHandler.cs:110` and `RemoveMemberHandler.cs:95` (BE-SEC-1).

**Which scopes exist.** Two, and both name an origin, not a resource level: `PermissionScope { Instance, Organization }` (`Mustask.Domain/Identity/PermissionScope.cs:10-17`) = "token" vs "membership". The catalog holds 20 codes: 3 instance, 17 organization (`PermissionCatalog.cs:90-112`), named `<module>.<resource>.<action>`, letters only (`PermissionCode.cs:12`, enforced over `AllCodes` by `Mustask.Domain.Tests/Identity/PermissionCatalogTests.cs:31`). Roles are the enum `Admin|Member|Viewer` with fixed bundles (`OrganizationRoleBundles.cs:12-42`): viewer = 7 read codes; member = viewer + `workitems.workitem.write`, `workitems.link.write`, `boards.backlog.reorder`; admin = every organization code, derived from the catalog (:23-24), so a new organization code lands in admin automatically (the matrix test forces the other two decisions, `OrganizationRoleBundlesTests.cs:57`). There are no project, team or area scopes, no project visibility, no per-project or per-team override, no custom roles (doc-001 BR-5 "no finer than the organization"; mod-016 spec § Out of scope; ADR-0027 "Revisit when").

**Org-level routes.** 44 routes carry an organization code (23 in `OrganizationEndpoints.cs`, 10 in `MembershipEndpoints.cs`, 7 work items, 3 boards, 1 process). The list is pinned: `OrganizationAccessInventoryTests.cs:236` asserts 44 against `OrganizationAddressedRoutes.All`. Team backlogs and boards sit under `/projects/{p}/teams/{t}/…` and need only `workitems.workitem.read` or `boards.backlog.reorder` (`BoardEndpoints.cs:34,42,52`): any member reads and writes every team's board. `assignee-candidates` is an organization route with no project id (`WorkItemEndpoints.cs:98`).

**How list reads are narrowed.** Only two reads depend on the caller: `GET /api/organizations` (EXISTS over the caller's membership, `OrganizationReadModel.cs:17-30`) and `/deactivated` (roles holding `organizations.organization.deactivate`, `GetDeactivatedOrganizationsHandler.cs:46`). Everything under an organization is narrowed by address and status only: projects `ListAsync(organizationId, status)` (`GetProjectsHandler.cs:48`), work items `GetPageAsync(projectId, …)` (`GetWorkItemsHandler.cs:47`), teams (the caller enters only as the `isMember` flag, `TeamReadModel.cs:25`), the area tree, assignee candidates (`ListMemberIdsAsync(organizationId)`). A team's backlog is "items of the project whose area resolves to the team" (`Infrastructure/Boards/BacklogMembership.cs:30-88`) — classification by area ownership, not access. No search, counter or autocomplete over items exists yet (feat-003 is queued).

**Team membership.** `TeamMembership(TeamId, OrganizationId, UserId)`: no role, no who/when (`Mustask.Domain/Organizations/TeamMembership.cs:12-50`). PK `(team_id, user_id)`; composite FK `(organization_id, user_id)` to the organization membership, ON DELETE CASCADE (`TeamMembershipConfiguration.cs:22-36`), so team members are organization members by constraint. It grants no code. It is read in three places only: the team list's `isMember` flag (`TeamReadModel.cs:25`) that the panel uses to default the team (`useOrganizationsContextSource.ts:379`, BR-M1-27); the team member list (`MemberReadModel.cs:41-54`); the add/remove/delete handlers. Writers: `CreateProjectHandler.cs:121` (creator joins the first team), `DeleteTeamHandler.cs:99` (ends memberships), the `AddOrganizationAccess` migration seed.

**Organization membership.** `OrganizationMembership(OrganizationId, UserId, Role, AddedBy/At, RoleChangedBy/At)`, PK `(organization_id, user_id)`, no FK to the user projection (`OrganizationMembershipConfiguration.cs:23-52`); the user key is the Keycloak `sub` string. The founder is added at organization creation (`CreateOrganizationHandler.cs:90`). Last-admin counting goes through the projection (`MemberReadModel.cs:68-87`). Existence of the row also gates the assignee rule (`MemberReadModel.cs:63-66`, `SaveWorkItemHandler.cs:246`; any role, a viewer included).

**Served to the panel.** `GET /api/organizations/{o}/access` returns `{role, permissions[]}` from the already-resolved role (`GetOrganizationAccessHandler.cs:24-27`). The panel's `AccessCheck(code, scope, organizationId)` has `PermissionScope = instance|organization|project|team`, but project and team only say which context an entry needs; every non-instance answer reads the organization's cached codes (`src/frontend/src/shared/lib/access.ts`, `features/organizations/access/servedAccess.ts:90-102`). One role per organization drives the role-change notice (`access/roleMemory.ts`); the bundles are hand-copied in `src/frontend/src/test/organizationRoles.ts`.

**Where a project/area/team scope would have to plug in (facts only).** (1) `OrganizationPermissionRequirement` / `OrganizationPermissionHandler` / `PermissionPolicies` / `EnsureScope` / `HttpContextOrganizationAccess` — all keyed on `organizationId` and a single role; (2) `OrganizationAccessReadModel` — one statement returning one role; (3) the nine handlers that repeat the project-in-organization chain, and the caller-agnostic read models and `IOrganizationStructure`; (4) the 44-route inventory and its 3-role matrix test; (5) `/access` and the panel's check; (6) `PermissionCatalog`/`PermissionScope` and the realm contract tests that compare only instance codes (`Mustask.Contracts.Tests/KeycloakRealmRolesTests.cs`).

## Responsibilities the current model carries (one duty per bullet; mark where one entity carries several duties)

- `OrganizationMembership` row — ONE ENTITY, FOUR DUTIES: (a) tenant visibility (no row = 404 for everything under the organization); (b) "my organizations" list; (c) eligibility to be an assignee (BR-M1-26); (d) eligibility to be a team member (BR-M1-10, composite FK).
- `OrganizationMembership.Role` — ONE COLUMN, SEVERAL DUTIES: (a) picks the code bundle; (b) membership administration authority and the last-admin guard (BR-M1-4); (c) project, team and area management (`*.write` are admin-only), so organization admin is also project manager, team lead and area manager; (d) which organizations may be restored (`*.deactivate`).
- `PermissionScope` — a code's origin (token vs membership); the brief's "scope" is where a grant applies. Same word, two duties.
- `PermissionCatalog` — registry, naming rule, Russian descriptions, and the comparand of the realm contract tests (instance subset).
- `RequiresOrganizationPermission` — three duties in one declaration: inventory category, enforcement, and the 401/404/403 order contract.
- `OrganizationAccessReadModel` — tenant resolution and organization liveness (active/deactivated) and role, in one statement; liveness is also a reachability duty (ADR-0026) elsewhere.
- `TeamMembership` — grouping people and choosing the default team (BR-M1-27); no access, no work ownership.
- `Team` — ONE ENTITY, SEVERAL DUTIES: a people group, the owner of a slice of work (through `Area.OwnerTeamId`), the holder of a default area, and (the first team) the root owner and the project creator's team (BR-M1-9, -11, -14).
- `Area` (project tree node) — classification path, team ownership with inheritance (`AreaTree.ResolveOwner`), default placement of new items. It has no access duty anywhere in Domain/Application/Api: area is not an authorization input today.
- `Project` — container of items, key, status, creator; not an authorization resource.
- `/access` response — carries both the role (panel notices) and the codes (visibility).
- Instance side (token) — dictionaries and organization creation; instance admin sees no organization content (doc-006 US-4).

## Rules and contracts the matrix model touches (by id: BR-M1-n, D-n, E-n, US-n, ADR-NNNN, api-contract §) — for each: what in the brief collides with it

- ADR-0027 rule 1 (two kinds of code, one catalog): brief § 10 wants Organization, Area, Project, Team scopes; the enum has two values that mean origin. Brief code examples (`workitem.read`, `workitem.change_status`, `area.manage`) fail `PermissionCode` (two segments, underscore) and `organizations.area.*` already means the project's area tree.
- ADR-0027 rule 2 / mod-016 spec matrix / api-contract § 0.2 (three fixed bundles; "a user's codes in an organization are exactly their bundle"): brief § 10 wants roles per scope (Area Manager, Project Manager, Team Lead…) and effective permissions from several grants.
- doc-001 BR-5, mod-016 spec § Out of scope, doc-006 "Release 2" and § Out of scope (custom roles; per-project and per-area overrides "release 2 or never"), ADR-0027 "Revisit when… a different role per project or team": brief § 10 is exactly the deferred item; each of these statements is superseded or amended.
- ADR-0027 rule 3 / BR-M1-6 / spec NFR "Access check" (one check from the address; membership read per request, no cache, no Keycloak, no projection, BR-M1-32): brief needs project, team and area ids and an area-tree walk in the same check; the NFR counts one indexed read.
- ADR-0027 rule 3 chain, spec § Resolution chains, mod-002 BR-M1-20/-22 ("t ∈ p ∈ o", "a team or an area never moves between projects", outermost-level 404): brief §§ 4-5 make teams and areas independent and M:N; the chain and its not-found order lose their meaning for teams and areas.
- ADR-0027 rule 4 / doc-006 BR-M1-8 / api-contract § 0.1 rows 2-4 (404 for non-members, 403 only for a member lacking the code, 403 before a nested 404): brief § 10.3 Restricted projects need a project-level non-disclosure; `RetrofitAccessTests.cs:27` pins "a viewer writing to a missing project gets 403".
- ADR-0027 rule 5 / BR-M1-31 / api-contract § 1.1 (`/access` = role + codes of one organization; re-read triggers): brief needs per-resource effective codes.
- ADR-0027 rule 6 (code first, then optional ownership predicate; no mechanism shipped): the brief's single effective-permissions service must fix where the predicate sits.
- BR-M1-30/-33 (one catalog; inventory test, exactly one organization code per route, 44 routes, 3x44 matrix): brief § 10.4 item 3 "consistent across APIs, boards, lists, single items" needs the inventory to cover scoped routes; the second-code pattern (`access.Holds`) is organization-role only.
- BR-M1-4 / BR-M1-32 (last known active admin): brief names Organization Admin; whether area/project/team admins count is unstated.
- BR-M1-5, BR-M1-10, BR-M1-36 (one membership per user per organization; team members ⊆ organization members; cascades): compatible with brief § 9 but § 5 gives teams "their own roles" and SC-04 "permissions are recomputed"; `TeamMembership` has no role column.
- BR-M1-25 (project creator joins the first team; seed): brief § 4 lets a project have no team; no first team to join; who may create a project (`organizations.project.write` is admin-only) vs a Project Manager.
- BR-M1-26 / mod-016 D-4 / doc-001 BR-13 (assignee = any active organization member, role irrelevant): brief § 6 "assignments are governed by access rights"; with Restricted projects an assignee may not see the item; the candidate route has no project id.
- BR-M1-27 / D-5 / US-7 (default team = the first team of the project's order the user is in; else the first team) vs the human's decision (project default team from settings, or inferred when exactly one team is linked): two defaults for one choice.
- BR-M1-35 / D-13 (deactivated lists and restore need `*.deactivate`, admin-only); mod-016 retrofit rows 1-37 (api-contract § 4) and § 3.3 additive fields (`isMember`): any change needs a note in mod-016 `status.md` (AGENTS.md; prior-art P-10).
- doc-006 § Roles ("team membership carries no role and no access: any member reads every team's boards") vs brief § 5 (team roles) and § 21 item 7 (do not tie task access only to team membership).
- mod-015 BR-8/-9/-18: the panel's single check and address prefixes put the team under the project; a cross-project Team Board has no address in that scheme.

## Risks and open questions for the analyst

- Names: which of "scope", "area", "inheritance" and `organizations.area.*` keeps its meaning? Today area inheritance is owner-team inheritance, not permission inheritance; the brief reuses both words.
- Must an organization membership remain the precondition for every grant (BR-M1-5/-8)? Brief § 9 "no team but access to a project" and SC-07 "explicitly assigned permissions" read both ways.
- Is the effective set additive only, or can a project deny? Restricted needs deny-by-default; "no implicit widening" (§ 10.4) needs a stated order against the 404/403/predicate sequence.
- Per-request cost: the NFR is one indexed read; area ancestors, `AreaProject`/`AreaTeam`/`TeamProject` links, visibility and scoped grants need more. Lists need "authorization filtering before data is returned", but every list read model and `IOrganizationStructure` is caller-agnostic today.
- Which answer discloses less for a Restricted project: 404 at project level (breaks the "403 before nested 404" row of api-contract § 0.1) or 403 (discloses existence)?
- What is "the provided administrative access" (§ 10.3)? Today organization admin holds every code; instance admin sees no content (doc-006 US-4); feat-033 wants a system admin without content access.
- Must an assignee hold read access to the item's project (BR-M1-26 says any active member, any role)? The candidate route has no project id.
- How does the panel learn scoped codes (one answer per organization today; role-change notice assumes one role)? Hand-copied bundles in `src/test/organizationRoles.ts` already drift-prone (tech-026).
- Team roles: where do they live if `TeamMembership` has no role; what do BR-M1-36 and SC-09 (unlink) do to them; is anything materialized (SC-04 "recomputed") or is it computed per request as today?
- Queue neighbours that move the base: tech-024 (Keycloak reduced to four client roles, role-to-code mapping into code; amends ADR-0018/0027), feat-033, feat-028 (BR-M1-25/-27 lapse), feat-002/mod-004 (first ownership predicate), tech-026. Order of landing is open.
- "Existing data may be dropped" is stated for the database; is the human's live Keycloak stand (mod-016 D-6) and its token-side roles in or out?
