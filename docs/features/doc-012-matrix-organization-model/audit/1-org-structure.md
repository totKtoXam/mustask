## As-is (what exists, with repository-relative file paths and line numbers where it matters)

- **Containment is a chain of mandatory parents: organization -> project -> {team, area}.** `teams.project_id` and `areas.project_id` are NOT NULL and there is no organization column on either; the organization is reached through the project (`B/Mustask.Infrastructure/Migrations/20261005092819_AddOrganizationStructure.cs:68-139`).
- `organizations`: name unique instance-wide over all statuses; `process_id` unique, so one process per organization (`...:14-38`, `:181-191`; `Domain/Organizations/Organization.cs:11-86`). `projects`: `organization_id` NOT NULL, name and key unique per organization over all rows, status Active|Deactivated (`...:40-66`; `Configurations/ProjectConfiguration.cs:31-37`). No project visibility/restriction field exists (`Domain/Organizations/Project.cs:29-47`).
- `teams`: name unique among the project's *active* teams; exactly one `is_first_team` per project (partial unique index) and a check it is never Deleted (`Configurations/TeamConfiguration.cs:37-51`; `Domain/Organizations/Team.cs:28-39`). `Team.Delete` is terminal, refused for the first team (`Team.cs:75-88`).
- `areas`: per project; `parent_id` null only for the one root per project (`ix_areas_project_id_root`); `owner_team_id` null = inherit; `default_of_team_id` marks a team's default area; composite FKs `(project_id, parent_id | owner_team_id | default_of_team_id)` onto the alternate keys `(project_id, id)` make the database refuse another project's parent or team; checks "default = owner" and "root is owned" (`Configurations/AreaConfiguration.cs:35-65`; `Domain/Organizations/Area.cs:34-51`). Cycles are refused by the domain only (`AreaTree.cs:79-84`, `Area.cs:104-125`); no database constraint, no trigger.
- `Project.Create` builds project + first team + root area, all named after the project, root owned by the first team for good (`Project.cs:55-74`). `Team.CreateWithArea` gives each later team its own default child of the root (`Team.cs:47-58`).
- Memberships (`20261011175557_AddOrganizationAccess.cs:14-64`): `organization_memberships(organization_id, user_id)` role admin|member|viewer; `team_memberships(team_id, user_id)` holds a *copy* `organization_id` with a composite FK to the organization membership (cascade) and a plain FK to `teams(id)`. Nothing in the database ties the copy to the team's own organization (`Configurations/TeamMembershipConfiguration.cs:27-36`; `Domain/Organizations/TeamMembership.cs:3-11`: "copied from the team's address chain once").
- Every route sits under `/api/organizations/{organizationId}/projects/{projectId}/…`: teams (`B/Mustask.Api/Features/Organizations/OrganizationEndpoints.cs:172-222`), areas (`:224-270`), team members (`MembershipEndpoints.cs:89-116`), team backlogs and boards (`Features/Boards/BoardEndpoints.cs:30-51`), work items (`Features/WorkItems/WorkItemEndpoints.cs:33-98`). The frontend mirrors it (`F/features/organizations/paths.ts:12-22`, `F/features/boards/paths.ts:7-15`).
- Reachability = containment, one place: active organization -> active project -> active team / any area (`Infrastructure/Organizations/Reachability.cs:30-52`, ADR-0026 rule 3). Tenant check = the handler's `IsReachableAsync(organizationId, projectId)`, then reads and locks by project id alone (`AreaRepository.cs:49-90`, `TeamRepository.cs:14-45`); `IOrganizationStructure` by-id reads are cross-tenant by design and callers compare ids (`OrganizationStructure.cs:74-152`, `Application/Features/Boards/GetBoard/GetBoardHandler.cs:36-44`).
- Not present anywhere: sprint/iteration/release code or tables (`grep -i "iteration|sprint"` over Domain, Application, Infrastructure, Api is empty; mod-007 is queued), an owning-team column on a work item, any project<->team, area<->project or area<->team link, and any scope below the organization in authorization.

## Responsibilities the current model carries (one duty per bullet; mark where one entity carries several duties)

- Organization — tenant boundary (every FK chain ends at `organizations.id`); owner of the single process; instance-wide name reservation; soft lifecycle.
- Project — container of work items and their number sequence (`work_item_counters`); key; **also the owner of the team set and of the area tree** (several duties: container + team set + classification tree).
- Team (several duties) — (1) a people group (`team_memberships`); (2) the owner of areas, hence of items; (3) the owner of backlog/board order (`backlog_orders` by `team_id`); (4) a child of one project, unique by name inside it; (5) soft-deleted with a cascade.
- Area (**five duties in one entity**) — (1) item classification path («Область»); (2) team-ownership routing, inherited down the tree; (3) the creation target of a team ("default area"); (4) the membership predicate of a team backlog/board; (5) a delete guard for items (`IAreaUsage`, `WorkItemAreaUsage.cs:13`).
- First team (several duties) — owner of the root, fallback owner when a team is deleted (BR-M1-18), the switcher's default team before mod-016 (BR-M1-24), default team again after it when the user is in no team (BR-M1-27).
- Root area — the "no team context" creation target (`ProjectInfo.RootAreaId`, `CreateWorkItemHandler.cs:127`).
- Organization membership — the only access source. Team membership — people<->team only; it feeds the `isMember` flag and the default team pick (`TeamReadModel.cs:25`), never an access decision.

## Risks and open questions for the analyst

- Name collision: the brief's Area (organization workspace, links to projects/teams) and today's Area (a per-project classification + ownership node) share a name, a table, `work_items.area_id`, two permission codes (`organizations.area.read|write`), six error codes and a URL segment. Do both survive under different names, or does the old one go and its classification duty (brief § 2: "separate those duties"; § 13 classification vs access) get a new mechanism?
- Silent emptying: team backlogs/boards are defined by area ownership (`BacklogMembership.cs:68`). Dropping area ownership without a stored `OwningTeamId` and a rewritten membership predicate empties every team surface; what do items with no team show on (P-2)? Today an item is on exactly one team board by construction (doc-001 BR-3); the brief allows none.
- `backlog_places` is keyed by work item (one place per item, any team): is rank per item, per (team, item), or per view once items move teams?
- Who may link or unlink: no operation exists today; each of project<->team, area<->project, area<->team needs a role and a surface (P-6), and SC-09 (block vs reassign) is left open by the brief. The unlink races with item creation and sprint assignment (ADR-0026 rule 8 would need a restatement, P-7).
- Database enforcement: the composite-key technique (mod-002 D-w) needs `organization_id` on projects, teams and areas (today only on projects) to guard `AreaProject`/`AreaTeam`/`TeamProject`; `team_memberships.organization_id` and `organizations.process_id` (deferred, tech-005) are existing unguarded copies. Cycle protection and "a team in a project only if linked" (§ 6 rule 4) have no database form today.
- Default team: stored column, link flag, or computed from "exactly one link"? What when that team is unlinked or deleted? The switcher's third level and the route `…/projects/{p}/teams/{t}/boards` cannot show a team across projects.
- Volumes: area trees are loaded whole per project and resolved in memory (`GetNodesAsync`, `BacklogMembership.AreaTreeAsync`); NFR is 500 nodes / 10 levels per project (mod-002 spec NFR). What are the organization-level numbers and the aggregation query shape?
- Overlap and sequencing: queued feat-028 (teams to the organization, `docs/backlog.md:23`) asks the same "what a team's backlog holds across projects" question; the mod-016 migration already expects regeneration (`AddOrganizationAccess.cs:92-93`); data may be dropped, so is the delivery one regenerated baseline or additive migrations?
- Contract breaks to name per delivery line (P-10): 26 mod-002 routes (plus team-member, board and work-item routes), 9 in-process consumers, 6 error codes with `docs/error-codes.md` generated from them, the frontend route table.
