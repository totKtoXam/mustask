# Spec: Matrix organization model (doc-012)

## Context and goal

Today a project contains its teams and its area tree, and a work item reaches its team only through the area it sits in ([audit 1](audit/1-org-structure.md), [audit 3](audit/3-work-items.md)). A team that works on three projects has to exist three times, a project cannot share a team, and access goes no finer than the organization ([audit 2](audit/2-access.md)).
The human's brief ([input-brief.md](input-brief.md), 2026-10-16) asks for a matrix model. Area, Project and Team become independent objects of the organization, linked many-to-many. A work item gets an optional owning team, sprints belong to teams and span projects, three levels of board read one item collection, and permissions are scoped, with project visibility.
This spec states the target behaviour, the fate of every existing rule it changes ([prior-art.md](prior-art.md) P-1) and the delivery lines. ADR-0028 (model) and ADR-0029 (scoped access) are drafted beside it and go to the human with it at gate-1. Two human decisions bind it (status.md): existing data may be dropped (§ Existing data), and a project has a default team (BR-MX-11).

## Roles

Access is still derived from membership (ADR-0027). An organization-level capability comes from the user's organization role or from a scoped grant held through that membership, never from the token. Instance roles (dictionaries, the right to create organizations) are unchanged and still see no organization content.
Each role is a fixed bundle of codes; ADR-0029 fixes the code strings and the matrix. The UI names describe capabilities, not job titles (brief § 10).

| Scope | Role (UI name) | Capability |
|---|---|---|
| Organization | admin «Администратор» | Everything on every object of the organization, Restricted projects included (OQ-3). Manages memberships. Creates projects, teams and top-level areas |
| Organization | member «Участник» | Reads the organization's members, areas, teams, links and sprints, and the projects whose visibility is «Организация». Reads and changes the work items of every such project, and orders their backlogs. Orders every team's backlog. On «Организация» projects and on teams this is today's bundle (mod-016 api-contract § 0.2); the project backlog's order is new (`feat-039-project-board`) |
| Organization | viewer «Читатель» | Reads what a member reads; changes nothing |
| Area | «Чтение» / «Изменение» | Reads, or also changes, the work items of the projects linked to the area or to an area that inherits from it, Restricted projects excepted (BR-MX-22) |
| Area | «Управление» | «Изменение», plus the area's name, description, place in the tree and «Наследовать доступ», creating child areas under it, managing the areas below it that inherit from it, its grants and the area's end of its links. Switching «Наследовать доступ» and moving the area away from its parent also need «Управление» on its current parent (the organization admin at the top level); removing an area–project or area–team link needs it on either end (BR-MX-3, BR-MX-6) |
| Project | «Чтение» / «Изменение» | «Чтение» reads the project's work items; «Изменение» also changes them and orders the project's backlog; a Restricted project included |
| Project | «Управление» | «Изменение», plus the project's settings (name, description, visibility, default team), its grants and the project's end of its links |
| Team | «Планирование» | Orders the team's backlog, as every «Участник» does; creates, renames, dates, starts, closes and removes the team's sprints; putting an item into one needs the right to change the item |
| Team | «Управление» | «Планирование», plus the team's name, description, members and grants, and the team's end of its links |

Belonging to a team (the people group) grants nothing on its own; ADR-0027 rule 2 is kept (brief § 21.7). A team's roles are team-scope grants. Every grant needs an active organization membership (BR-MX-20).

## Glossary

| Term | Meaning |
|---|---|
| Organization | The tenant: the root object and the only isolation boundary. Every object and relation below belongs to exactly one organization |
| Area («Область») | A workspace of the organization: a name, a description, an optional parent area (so areas form a tree), links to projects and teams, participants, and an inheritance switch. It owns nothing — projects and teams are linked to it, never stored inside it. It replaces the per-project area tree (OQ-1) |
| Project | Owns its work items, their numbering and its identifier key. Independent of teams and areas. Has a description, a visibility and an optional default team |
| Team | A group of the organization's people, with a description, that delivers work in the projects it is linked to. Owns its backlog order and its sprints |
| Link | A many-to-many relation inside one organization: project–team (the team takes part in the project), area–project, area–team. A link has no fields beyond who made it and when (BR-MX-20); only an area–project link carries access, and only for holders of grants on the area (BR-MX-7) |
| Owning team | The single optional team responsible for a work item, shown as «Команда» («Без команды» when empty). It is always a team linked to the item's project |
| Project default team | The team a new item of the project starts with outside a team context: the team set in the project's settings, else the only linked team, else none |
| Sprint | A team's time-boxed plan («Спринт»). It holds items of any of the team's projects and goes Planned → Active → Closed |
| View | A backlog or a board, at team, project or area level, over the one collection of items; never a copy |
| Grant / participant | A grant is a role of one scope (area, project or team) held by an organization member on one object. An area's participants are the users whose grants reach it (BR-MX-22): held on the area itself (direct) or on an ancestor it inherits from (inherited). The brief's (§ 9) area membership and project participation are these grants or, for a «Организация» project, the organization role (BR-MX-23); a member with no role would hold nothing, so there is none. Team membership stays a relation of its own and grants nothing |
| Visibility | A project's setting that decides who may see the project at all: «Организация», «Участники областей» or «Ограниченный» |
| Effective permissions | The codes a user holds on one object, computed by one deterministic algorithm (BR-MX-23, ADR-0029) |

## Business process (BPMN)

```mermaid
flowchart TD
    S([Organization admin structures the organization]) --> A1[Create or move areas: top level by the org admin, under a parent with «Управление» on it, a move also with it on the current parent]
    A1 --> A2{New parent is the area itself or a descendant, deeper than 10 levels, or the name taken among its siblings?}
    A2 -->|yes| A2x[Refused, tree unchanged]
    A2 -->|no| P1[Create projects and teams; nothing else is created with them]
    P1 --> L1[Link project-team, area-project, area-team]
    L1 --> L2{Each end, the requesting end first: in this organization, active, and «Управление» held on it?}
    L2 -->|no| L2x[Not found or 403 per BR-MX-24, nothing linked]
    L2 -->|yes| G1[«Управление» holders grant scoped roles and set each project's visibility and default team]
    G1 --> W1[A user with the item code creates a work item in a project]
    W1 --> W2[Owning team from the parent, else the team surface, else the project default team, or none]
    W2 --> W3{Team linked to the item's project?}
    W3 -->|no| W3x[Refused, item not saved]
    W3 -->|yes| SP1[A team planner plans a sprint with items of several projects]
    SP1 --> SP2{Item owned by the sprint's team?}
    SP2 -->|no| SP2x[Refused, sprint unchanged]
    SP2 -->|yes| V1[Members open the team, project and area boards]
    V1 --> V2{User may see the item's project?}
    V2 -->|no| V2x[Item absent from views, counters, search; its address answers «Проект не найден»]
    V2 -->|yes| V3[Item shown once, with its project and owning team]
    V3 --> U1[A manager of both ends unlinks a team from a project]
    U1 --> U2{Team owns items in that project?}
    U2 -->|no| U3[Link removed]
    U2 -->|yes| U4{Target chosen: another linked team or «Без команды»?}
    U4 -->|cancelled| U4x[Nothing changes]
    U4 -->|chosen| U5[One operation: items reassigned, their pointers to the team's sprints cleared, default-team setting cleared if it named the team, link removed]
```

## Business rules

| # | Rule | Source |
|---|------|--------|
| BR-MX-1 | **Tenant boundary.** Every area, project, team, link, membership, grant, sprint and work item belongs to exactly one organization. Every read, write, lock, counter and search stays inside the organization in the address. An id from another organization anywhere in a request — address, body, link end, owning team, sprint, parent or assignee — gets the same answer as an id that names nothing, and changes nothing. | brief § 3.1; mod-002 BR-M1-22; P-3 |
| BR-MX-2 | **Independent existence.** An area, a project and a team can each exist with no link of any kind, and an organization may have no areas at all. Creating a project creates no team, no area and no team membership; creating a team creates no project and no area. Unlinking or deleting one object never deletes another object or a work item. | brief §§ 3.1-3.2, 4.1-4.2, 5.1, 11.5; SC-07 |
| BR-MX-3 | **Area tree.** An area has at most one parent, which is an area of the same organization. A move carries the area's whole subtree. A move whose destination is the area itself or one of its descendants is refused, so the tree never holds a cycle, concurrent moves included. The tree is at most 10 levels deep. A move needs «Управление» on the area and on its new parent; creating a top-level area, or moving one to the top level, needs the organization admin. Switching «Наследовать доступ», or moving an area away from its parent, also needs «Управление» on its current parent (the organization admin at the top level); in a one-operation create, «Управление» is checked on the parent for everything the form sets, its participants and the switch included, and the switch is applied last. Turning the switch off ends the actor's own inherited «Управление» on the area. A move or a change of «Наследовать доступ» takes effect for every project linked to the area or its subtree, and needs nothing from those projects; a project that must not widen is «Ограниченный». | brief § 3.2, SC-08; mod-002 BR-M1-12 |
| BR-MX-4 | **Names and descriptions.** An area's or a team's name is 1–100 characters after trimming and is compared ignoring letter case and surrounding spaces. A team's name is unique among its organization's active teams. An area's name is unique among its siblings, and the organization's top-level areas count as siblings of each other. Project names and keys keep mod-002 BR-M1-1. An area, a project and a team each have an optional description of at most 2 000 characters, kept as typed. | mod-002 BR-M1-1; audit 1 (no uniqueness guard for top-level areas); brief § 11.5 |
| BR-MX-5 | **Links.** There are three kinds: project–team, area–project and area–team. Each is many-to-many, with at most one link per pair. Both ends must be active — a project that is not deactivated, a team that is not deleted — and in the same organization. Linking a pair that is already linked, or unlinking one that is not, changes nothing and is not an error. | brief §§ 3.2, 4.3-4.4, 5.2-5.3, 12 |
| BR-MX-6 | **Who links.** Creating a link needs «Управление» on both ends, and so does removing a project–team link, which reassigns items (BR-MX-12); removing an area–project or an area–team link needs it on either end. The organization admin holds it on every object. A link gives no power over its other end beyond ending the link: nobody renames, moves, deletes or reconfigures an area or a team through a project, or the other way round. | P-6, P-9 |
| BR-MX-7 | **Links disclose nothing by themselves.** A project–team or area–team link grants no code and never makes a project visible. An area–project link is the one path by which grants on an area reach a project and its items (BR-MX-21 «Участники областей», BR-MX-22); it never reaches a «Ограниченный» project and gives nothing to a user whom no area grant reaches. | brief §§ 5, 10.3-10.4; SC-05 |
| BR-MX-8 | **Area deletion.** An area can be deleted only when it has no child areas, by a holder of «Управление» on it. Its links, those to projects the actor may not see included, and the grants held on it end with it, and nothing else changes: no project, team, item or other area. The confirmation names its team links, its links to projects the actor may see (a deactivated one marked «деактивирован») and its grants; a link to a project the actor may not see ends unnamed and uncounted (BR-MX-21). Unlinking an area from a project or a team removes only that link. | brief § 3.2 |
| BR-MX-9 | **Owning team.** A work item belongs to exactly one project, which no team, area, link, board or sprint operation changes; moving an item to another project is out of scope. It has at most one owning team, and that team must be linked to the item's project when it is set. Changing the owning team does not change the item's project, identifier, assignee, history or estimates. The assignee need not belong to the owning team. | brief § 6 rules 1-8; SC-04 |
| BR-MX-10 | **Creation defaults.** A new item's owning team starts as follows. Created as a child, on any surface: its parent's owning team as stored when the child is saved, or the project default team (BR-MX-11) when the parent has none. Otherwise, created from a team's surface: that team. Otherwise: the project default team, or «Без команды» when the project has none. In a creation dialog the creator may change it, before saving, to any linked team or to «Без команды»; a row's or a checklist's add has no «Команда» field. | human decision; brief § 6 |
| BR-MX-11 | **Project default team.** If the project's settings name a team, that team (it must be linked) is the default, marked «По умолчанию». If they name none and exactly one team is linked, that team is the default, marked «По умолчанию: единственная команда». Otherwise the project has no default team. Unlinking or deleting the team the settings name clears the setting in the same operation, and the rule above applies again. The default affects BR-MX-10 only. | human decision (status.md 2026-10-16) |
| BR-MX-12 | **Unlinking a team that owns items (SC-09).** A team may own items, in any state, in a project it is being unlinked from. The actor then chooses, in the confirmation, one destination for all of those items: another team linked to the project, or «Без команды». In one operation the items take that owning team, lose their pointers to the unlinked team's sprints and arrive unplaced on the destination team's backlog; the default-team setting is cleared if it named the unlinked team; and the link is removed. A save or creation that sets the unlinked team concurrently either commits first and is reassigned with the rest, or comes after the unlink and is refused with «Команда не участвует в проекте.»; the confirmation counts what the team owned when it opened, and the request always names its destination («Без команды» when the dialog offered none). A destination that is the unlinked team, or is not linked to the project when the unlink runs, answers «Команда не участвует в проекте.», a deleted, foreign or unknown one «Команда не найдена.», and nothing changes. Each reassigned item's «Изменён» becomes the operation's time. Deleting a team (organization admin; soft; no restore; the name becomes free) applies this unlink to every project, deactivated ones included, with «Без команды» as the destination, and also ends the team's area links, memberships and grants. The rule reassigns rather than blocks because deleting a team already moves its work in one confirmed operation (mod-002 BR-M1-18). With no bulk edit, a block would leave the manager editing the items one by one. | brief SC-09, § 6 rule 9; P-7 |
| BR-MX-13 | **Sprint and team.** A sprint belongs to exactly one team, permanently, and may hold items of any project. An item's sprint, when set, is always a sprint of the item's current owning team, so an item with no owning team has no sprint. A save that changes the owning team clears the sprint, unless the same save sets a Planned or Active sprint of the new team. The pointer is cleared the same way, a Closed sprint's included, when the team is unlinked from the item's project or deleted (BR-MX-12); a Closed sprint's outcome keeps the item (BR-MX-14). | brief §§ 6.10, 8.1-8.4; P-8 |
| BR-MX-14 | **Sprint lifecycle.** A sprint goes Planned → Active → Closed and never back. A team has at most one Active sprint (OQ-6). While a sprint is Planned its dates are optional, but come as a pair with finish ≥ start; starting a sprint needs both dates. An Active sprint's dates may change but not be cleared; a Closed sprint may be renamed, and its dates never change. Items join only Planned and Active sprints. Closing moves, in the same operation, every item in the Proposed, In Progress or Resolved category to a Planned sprint of the team, or to no sprint, and records the outcome: the sprint's items in the Completed category at that moment, with their project and story points then. The record never changes, whatever happens to those items later. Completed items and items in «Удалена» keep the Closed sprint as their sprint until a save changes it; an item reopened later keeps it too, and no close moves it. A Closed sprint's page and figures show its outcome; the «Спринт» filter matches the items whose sprint it currently is. A Closed sprint takes no new item and is never removed. A Planned sprint that holds no item outside «Удалена», a deactivated project's items included, may be removed, and the removal clears its items in «Удалена». A deactivated project's items are moved and recorded like any others, and count on no sprint board, outcome or overview figure until the project is restored. A deleted team's Closed sprints and their outcomes stay listed, read-only, on the «Спринты» of the projects whose items they record (the human, gate-1, 2026-10-17); one whose outcome recorded no item records no project and is listed on none. **Sprint board.** The team's «Спринты» holds a board of its Active sprint, with «У команды нет активного спринта.» and a way to the sprint list when there is none. It shows one mod-006 level at a time, in the organization process's columns for the level (BR-MX-19) and the team's order of that level (ADR-0028 § 9). A card move writes its item's state as on the team board (BR-MX-18), and the board has no reorder. Its totals are the items and story points of the shown level, after visibility (BR-MX-21). **Races.** A close and a save into the sprint, the removal of its destination, an unlink or deletion of its team, or a save that changes the owning team of one of its items, and a removal and a save into the sprint, each end in one order and no server error: the request that locks second re-reads, and either is refused or completes on what the first left (ADR-0028 § 10). | brief §§ 8.5, 8.6; P-8 |
| BR-MX-15 | **Sprint numbering.** A team's sprints are numbered 1, 2, 3… in creation order, and a number is never reused. The default name is «Спринт <n>». Names are unique among the team's sprints, and renaming keeps the number. A sprint's name is 1–100 characters after trimming and is compared ignoring letter case and surrounding spaces; a removed sprint frees its name, never its number. | brief § 8 (the «Sprint 12» case) |
| BR-MX-16 | **No copies.** An item exists once. Every view, list, counter and aggregate shows or counts it at most once, however many areas, links or sprints lead to it. A change of its state shows in every view. | brief §§ 3.2, 7, 21.8; SC-03, SC-06 |
| BR-MX-17 | **View contents.** Views exist per mod-006 level («Эпики», «Фичи», «Истории») and hold every state outside Removed. A team's views hold the items the team owns, in all its projects. A project's views hold every item of the project, whatever its team or with none. An area's views hold the items of the projects linked to the area and, when «Включая дочерние области» is on, to its descendants. The switch is one choice per user and area, shared by the area's backlog, board and overview, and is on until the user turns it off (doc-001 BR-15). Area views offer no create command. Every view then leaves out the items the user may not see (BR-MX-21). An area's overview also shows the Active sprint of each team linked to the area, counted as that team's sprint board counts it for the user, whatever the items' projects (brief § 8.8). | brief §§ 7.1-7.3; SC-01..SC-03, SC-05, SC-08 |
| BR-MX-18 | **Order.** A team's backlog keeps its own order per team and level, and a project's backlog keeps its own per project and level; reordering one never changes the other. An area's views have no order of their own and sort by a chosen column. Unplaced items sort by creation time, then by project key and number, so items of different projects never tie. A card move writes only its item's state, in the item's own project. Neither a card move nor a reorder changes an item's project or owning team. | brief § 7; P-2; doc-001 BR-12 |
| BR-MX-19 | **Statuses on shared views.** A view's columns are those the organization's process gives the level, whatever items it shows (mod-002 BR-M1-3, OQ-2). A move offers only the states of the card's own type in its own project's process. No status is ever rewritten to make columns match. The line that lets projects' processes differ owes the shared-view columns: state categories over the projects the view can show and the user may see, whatever the filter or page (ADR-0028 rule 11), with a drop target per state of the card's own type. | brief § 7, SC-10 |
| BR-MX-20 | **Grants.** A grant is held by an active organization member; adding a non-member is refused. Removing a user's organization membership ends every grant and team membership they hold in that organization. The roles are the fixed bundles of § Roles: there are no custom roles and no denying grants. Every grant and link records who made it and when. | brief §§ 9-10.2; mod-016 BR-M1-5, -10 |
| BR-MX-21 | **Visibility.** A project has exactly one visibility, «Организация» when it is created. «Организация»: every organization member sees it, through their organization role. «Участники областей»: visible only to organization admins, to holders of a grant that reaches an area linked to it (BR-MX-22) and to holders of a grant on the project. «Ограниченный»: visible only to organization admins and to holders of a grant on the project; area grants and links never reach it. A project a user may not see does not exist for them. It is in no list, switcher, view, counter, aggregate, search, picker, «ещё» flag or overview figure. Its address and the addresses of its items answer «Проект не найден». Two refusals are accepted exceptions and name nothing more: a rename to a hidden project's name is refused as taken (project names stay unique in the organization, mod-002 BR-M1-1), and a Planned sprint that holds hidden items is not removable (BR-MX-14). | brief §§ 10.3-10.4; SC-05, SC-06; P-4 |
| BR-MX-22 | **Inheritance.** A grant on an area reaches that area and its descendants. It stops at a descendant whose «Наследовать доступ» is off: that area and its subtree receive nothing from above, while the grants held on them still apply. An area grant reaches the work items of the projects linked to the areas it reaches, unless the project is «Ограниченный». A team grant reaches only the team itself — its settings, members, backlog order and sprints — and never the items of the team's projects, except that closing the team's sprint moves its unfinished items (BR-MX-14). No grant passes from one area to another through a shared project or team. | brief §§ 10.1, 10.4; SC-05, SC-08 |
| BR-MX-23 | **Effective permissions.** An organization admin holds every code on every object (OQ-3). For any other user, the codes on an object are the union of two sources. The first is the bundle of their organization role: always on the organization, its areas, teams and sprints, and on a project and everything in it only when the project's visibility is «Организация» (ADR-0029 § 6 step 4). The second is the bundles of every grant that reaches the object (BR-MX-22). Visibility (BR-MX-21) is applied first. Codes are only ever added. The same memberships, grants, tree and links always give the same result, whatever their order. The server computes it in one policy, for every route, list, counter and search; the panel only reflects it. A change takes effect on the user's next request. | brief § 10.4 items 1-6; P-5 |
| BR-MX-24 | **Answer order.** An organization-addressed request gets the first of these that applies: 401 when the user is not signed in; «Организация не найдена» when they are not a member; «Проект не найден» when the project the request is made in is missing, deactivated (its restore excepted) or not visible to them; then the not-found of every other id in the address, outside in: «Команда не найдена» or «Область не найдена» (for a new child area, its parent), then the sprint's or the work item's; 403 when they see the object the request acts on but lack its code; then the field errors. Every other id the request names — a link's other end, a move's destination, an owning team, a sprint, a parent, an assignee, a grantee or a new team member (a user who is not a member answers «Участник не найден.») — is checked after those: it answers its own not-found, then 403 if its own code is lacking. A foreign id gets the answer of an id that names nothing, so no answer tells whether a hidden object or another organization's exists. | ADR-0027 rule 4, amended; ADR-0029 § 8 |

## Non-functional requirements

- **Non-disclosure:** each surface BR-MX-21 names has a test comparing a user who cannot see project X with the same data without X. The answers are identical, totals and «ещё» flags included, BR-MX-21's two named exceptions aside (brief § 10.4 items 4 and 7; P-4).
- **Tenant isolation:** every new route, link and lock passes the containment check that applies to today's routes: foreign ids answer «not found» and change nothing (P-3).
- **Volumes:** an organization with 1 000 areas (10 levels), 200 projects, 200 teams, 2 000 members, 10 000 grants and 100 000 items. A team or project backlog of 5 000 items returns within 2 s, as in mod-006. Area views and the work item list return pages of at most 50 rows within 2 s, including the first page of an area view over 50 000 items of at least 10 projects. A single-item read returns within 500 ms, its access check included. Closing a sprint, and an unlink or a team deletion that reassigns items, complete within 5 s for up to 5 000 affected items, all or nothing (doc-004's bulk-write NFR, carried over).
- **Client load:** no request returns the items of more than one view, and the panel never loads every item of the organization. A board or backlog draws at most 2 000 rows at a time (feat-027 BR-T-7). Area views and the work item list page on the server; team and project backlogs stay whole-level reads, as in mod-006, because a reorder is made against the whole level; within the budget a team's or a project's level holds at most 5 000 items; above that the read stays whole and has no time budget, an accepted risk revisited when a project nears it.
- **Query shape (brief §§ 14, 17):** a view, a list, a figure or an access check reads its rows, their projects and teams and the caller's access in a number of statements that does not grow with the rows, projects, teams, areas, tree depth or grants (no N+1); a statement-count test pins it per surface. The views and the «Рабочие элементы» list take their filters from one shared specification, which feat-003 founds for the list and feat-013 extends to the views (doc-010 D-14); a line that adds a filter earlier (the owning team's, the project's) founds it if it is first and adds to it otherwise, so a filter means the same on every surface (US-10, US-11).
- **Concurrency:** two requests can each pass on their own yet break a rule together — two area moves that would form a cycle; an unlink and a save that sets that team; a sprint close and a save into the sprint; a link and the deletion of either end. In each case the two are ordered: the earlier commits and the later is refused (doc-001 BR-11) or, for an unlink or a close that meets a save, takes the save's item in with the rest (BR-MX-12, BR-MX-14); none ends in a server error. A change of access — a grant, a role, an area link, a parent, an inheritance switch or a visibility — is not such a race: a request is decided by the access committed when its check runs, and one checked before the change commits completes as if it ran first (ADR-0029 § 7, as ADR-0026 rule 8).
- **Observability (brief § 17):** each refusal by the access policy is logged with the route, the code, the resource scope and the user id, never with a hidden project's name; each migration that drops rows logs, per table, how many it dropped.
- **No new dependencies (brief §§ 11.6.1, 11.6.8, 17, 21.14):** no new library, service or infrastructure. The panel keeps the UI kit (tech-015) and ADR-0024's visual language, and every new page and dialog works down to ADR-0024's 640 CSS px floor.
- **Regression:** every test listed under "Regression surface" in the audits stays green, except tests that encode a rule this spec retires or replaces. Each line retires those tests by name, citing the rule id (P-1). "Green" means `scripts/verify.sh` (P-11). E2E specs, outside `scripts/verify.sh`, are not part of "green": each line answers the E2E question per task (routing.md) and names in its MR the specs its address changes break, and the SC-01..SC-09 clauses run through their stories' owed-by re-runs (brief §§ 16, 18.6).
- **Localization:** all interface copy is Russian (AGENTS.md).
