### Findings

- **F1 — major — `AGENTS.md:64-67`** (also `docs/ai-workflow/feature.md:55-58,106-108` and `scripts/handoff.sh:180-182`): requiring every QA/review session to prove the task worktree **and branch** conflicts with the live reading-role convention in `docs/conventions/git.md:258-268`. That convention puts code review and QA re-checks in their own detached checkout; `git branch --show-current` is empty there, and their host root is their reader checkout. Such a compliant reader can never satisfy the new prerequisite, while switching the existing writer checkout would defeat the isolation the convention describes. **Fix:** state the reader case explicitly throughout the binding instructions: writers prove the existing task checkout and branch; permitted detached readers prove their actual bound reader root, Git toplevel and expected task commit. Keep the support/confirmation and interactive-transfer requirements for both cases. Alternatively align the reading-role convention to a deliberately chosen replacement model before requiring it.

- **F2 — major — `docs/ai-workflow/feature.md:62-69`** (blocking continuation instruction: `scripts/handoff.sh:178-179,194-198`): when native relocation is unavailable immediately after `new-task`, step 5 stops the original session before step 6 records the confirmed route/size grounds and takes the queue line. `new-task.sh:288-320` only creates the initial status skeleton; `handoff.sh:125-127` already calls the task started as soon as its branch exists. Consequently the replacement receives a prompt that prohibits `queue.sh take` and goes directly to the implementation stage, leaving startup bookkeeping unfinished and its missing route grounds in the old conversation. **Fix:** complete the route Log and queue-only startup bookkeeping before the binding/stop boundary, explicitly allowing only this orchestration work and handoff preparation there; implementation, QA, review and delegation must still wait for confirmed binding. Align the generated queued-task instructions and `new-task` next steps with that order. Another valid fix is to persist a startup-pending state and have the receiving prompt explicitly complete it before stage work.
