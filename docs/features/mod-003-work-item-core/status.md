## Plan

1. Domain `Mustask.Domain/WorkItems`: `WorkItem` (number, type, state, assignee, area, title, description, created/changed), the title and description rules, `WorkItemIdentifier` (format and parse), the type's state set (initial state, allowed states), `WorkItemsErrorCodes`; `workitems.workitem.read/write` in `OrganizationPermissionCatalog` (not in the realm).
2. Storage, one migration `AddWorkItems`: `work_items` (FKs to the project, `(project_id, area_id)` → `areas`, the type, the state; unique `(project_id, number)` and `(project_id, creation_request_id)`) and `work_item_counters` (the per-project last number).
3. Five slices in `Features/WorkItems` (list, create, read, save, assignee candidates) behind `AuthenticatedOnly` + mod-002's organization-context filter; the area picker uses mod-002's tree read and the type picker mod-001's process read, unchanged.
4. Numbers (BR-M3-5): the counter row is locked `FOR UPDATE`, so creations of a project serialize; the replay of a submission (BR-M3-26, a client `requestId`) is checked after that lock, so a replay consumes no number.
5. Save (BR-M3-25): a `PATCH` of the sent fields only, the item locked `FOR UPDATE`, a new area locked `FOR SHARE`; mod-002's deletion keeps its `FOR UPDATE` and now asks a port `IAreaUsage` (M1 declares it, M3 implements it) after the lock (BR-M3-24).
6. Tests: domain units, handler units where a rule lives in the handler, an integration test per endpoint, races with mod-002's commit gate, the inventory of organization-addressed routes. No lanes: the five use cases share one repository and read model.

Frontend (stage 6):

7. Slice `features/workitems`: `api/workItemsApi.ts` (contract § 1–§ 2, one function per route), `api/queryKeys.ts` (`['workitems', 'list' | 'item' | 'assigneeCandidates', …]`), query and mutation hooks — create invalidates the project's list, save puts its answer in the item's cache and invalidates the list; mod-001's process read and mod-002's area tree come through their barrels, unchanged (contract § 3).
8. Pages and routes: «Рабочие элементы» at `…/projects/:projectId/workitems` (`PageHeader` with the primary and the type picker `Menu`, `Table` + `TablePagination` 50 rows, `RegistrySkeleton`, `ErrorBanner`, the empty `StateFrame`, `NotFound`); the form at `…/workitems/:identifier` (a band with the `h1`, the `InputBase` title and «Сохранить»; a strip with `TextField select` «Статус», `Autocomplete` «Исполнитель» and «Область»; `TextField multiline` «Описание»; band/strip skeletons + `FormSkeleton`).
9. Components: `CreateWorkItemDialog` on `FormDialog` (one `requestId` from `crypto.randomUUID()` per dialog session, kept across retries), `StatePicker`, `AssigneePicker` (debounced search, hint rows as disabled options), `AreaPicker` (tree read on first open, retried on reopen), the band; a page-level `Snackbar` notice.
10. State: server state only in TanStack Query; the form's draft is local and diffed against the loaded item, so «Сохранить» is enabled only on a difference and the `PATCH` carries only the changed fields; the list's page is local.
11. Logic in `lib/`, unit-tested: the title and description checks, refusal placement by `errorCode` (field, `Alert` or frame), the not-found level, the `PATCH` diff, the assignee label («Не назначен», «Неизвестный пользователь»), the editable states (no `Removed`).
12. Shared and shell: `NotFound` gains the `workItem` level; `PageHeader`'s command gains `endIcon` and a menu flag (`aria-haspopup`, `aria-expanded`); `TypeMark` and the category marker move to `shared/ui` and `initials` to `shared/lib` (two consumers each); `workItemErrorCodes` in `shared/api` with a drift test; the «Рабочие элементы» entry (`ListAltOutlined`, `workitems.workitem.read`, project scope) in the work group and the two routes.
13. Tests: component tests (Testing Library + MSW over an in-memory work item API) named after each US-1..US-6 scenario with a panel half, a shell routes test, and `e2e/specs/22-work-items.spec.ts` (listed, not run here).
