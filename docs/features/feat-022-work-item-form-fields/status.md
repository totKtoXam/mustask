## Plan

<!-- S/M: implementation plan, 3-10 lines. L: see plan-backend.md / plan-frontend.md -->

Backend (stage 4, 2026-10-09; contract: api-contract.md). No lanes: one write slice (the save) and three reads change, not four independent use cases.
1. Domain `Mustask.Domain/WorkItems`: `WorkItemField` and `WorkItemFieldSet` — the fields per type, the type recognised by its appearance token, never by name; `WorkItemFieldRules` — list keys, 0..9 999 with two decimals, the integer, 2000–2099 dates, 100 000-character texts, the defaults; enums `WorkItemActivity`, `WorkItemValueArea`. `WorkItemTypeStates` gains the appearance. `WorkItem` gains the 17 values: `Create` sets BR-M3-37's defaults, `CheckFields` answers every reason (not on the type, the value, target before start against the stored dates), `Save` applies `WorkItemFieldsEdit` (empty → default on the three always-set fields).
2. Infrastructure: `WorkItemConfiguration` columns and checks; migration `AddWorkItemFormFields` (priority 2 on every row by column default; severity, value area and the type's texts back-filled by the type's appearance; `changed_at` untouched; Down drops the columns); `WorkItemReadModel` and `BacklogReadModel` project the fields, numbers in their shortest form.
3. Application and Api: `SaveWorkItem` takes the 17 fields (texts as strings, the others as `{ value }`), merges their reasons into mod-003's step-2 400; `CreateWorkItem` unchanged but for the defaults; `WorkItemView` gains the fields, `BacklogItemRow`/`BacklogItemView`/`BacklogRowView`/`BacklogChildView` gain `priority`.
4. Contracts: eight codes in `contracts/errors/workitems.json`, `docs/error-codes.md` regenerated, the panel's constants and drift test; mod-003's and mod-006's contracts and Logs note the additive change.
5. Tests: domain unit tests of the rules; integration tests per US-1..US-6 scenario, the refusals, empty versus unchanged, the cross-type refusals; the back-fill of existing items in a migration test (Infrastructure.Tests); the backlog volume test within its budget.

Frontend (stage 6, 2026-10-09; no new slice, route or dependency; MUI core only).
F1. `features/workitems` API and draft: `WorkItem` gains the 17 fields (`WorkItemFields`), the save body `{ value }` wrappers and string texts; `lib/fields.ts` — the fields, lists, ranges and sections per type by `type.appearance`; `lib/fieldValues.ts` — held as the control holds them, compared as numbers, the browser's checks, only the type's changed fields sent; field reasons on their fields, `field_not_on_type` in the Alert.
F2. The form: the «Детали» grid (CSS grid, `useMediaQuery` at `lg` = 1280 px, 8/4, one column below with the right column's controls at `layout.formColumnWidth`); `FormSection` (`h2` region), `FieldControl` (`TextField select`, number `TextField` with its input mode, `TextField type="date"`); the type's texts under «Описание»; feat-001's «Связанная работа» last in the right column (mod-015 § 10.3); a `FormSkeleton` per column while loading. Server state stays TanStack Query; the draft stays local state.
F3. `features/boards`: `BacklogItem.priority`; the backlog column «Приоритет» after «Статус» (and its skeleton); the card's third line «Приоритет: <n>» (`caption`).
F4. Tests: unit (fields, values, draft, refusals, API), component per US-1..US-6 scenario, E2E spec 25 (listed, not run).
