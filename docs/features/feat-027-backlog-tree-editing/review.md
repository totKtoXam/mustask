#### B-1 / C1 — Building the row views recurses once per tree level with no bound, so a deep enough chain overflows the stack and kills the API process

- **Where:** `src/backend/Mustask.Application/Abstractions/Boards/BoardViews.cs:141`
- **Scenario:** BR-H-2 sets no depth limit, and a bug under a bug or a task under a task is allowed. Any signed-in user can build a chain of a few thousand same-level items. Since this task it costs one call per link: `POST …/workitems` with `parentId` = the previous item, which also takes that item's area, so the whole chain stays on one team. The next GET of that team's «Истории» (or «Фичи» / «Эпики», wherever the chain's root shows) goes through `BacklogTree.Nest`, which is iterative and returns fine. Then `BacklogRowView.Tree` → `BacklogChildView.Of` calls itself through `Select(...).ToList()` for every level: Of → Enumerable.ToList → ListSelectIterator.ToList → Fill → lambda → Of. That is about five frames per level. This all runs inside the handler, before the serializer's MaxDepth check can throw. With thread-pool stacks of about 1–1.5 MB, a chain of a few thousand links is enough (an estimate; I did not run it). A StackOverflowException cannot be caught, so the whole API process dies, for every organization. It dies again on every later open of that page, which the panel does on navigation, until someone breaks the chain. `Nest`'s own doc claims "no depth of the tree can exhaust the stack". The 10 000-link domain test proves this for `Nest` only. The endpoint test stops at 40 links. So the guarantee the design was built for is cancelled by the very next call.
- **Evidence:** BoardViews.cs:141 `row.Effort, row.BusinessValue, row.ValueArea, parents.Of(row), Of(node.Children, rows, parents));` inside `internal static IReadOnlyList<BacklogChildView> Of(...) => nodes.Select(node => { ... }).ToList()` (line 132). BacklogTree.cs:34-36: "the walk ... is a loop, not a recursion, so no depth of the tree can exhaust the stack". BacklogTreeTests.cs:154-177 `Nest_AVeryDeepChain_NestsToItsEnd` (10 000, domain only). BacklogTreeEndpointTests.cs:183-219 (40 links). feat-001 spec BR-H-2: "There is no depth limit." feat-027 api-contract § 3 item 8: "a bug under a bug are allowed".
- **Proposed fix:** Build the `BacklogRowView`/`BacklogChildView` graph without recursion: walk `Nest`'s nodes post-order with an explicit stack, then construct each view once its children's views exist. Or make the depth bound a decision (see C2) and refuse or truncate past it before any recursive code runs. Add an endpoint-level test with a chain deeper than the writer's limit that asserts a defined answer, not a crash.

#### B-1 / P1 — The backlog view mapping recurses once per tree level, so a long same-level chain can overflow the stack and kill the API process

At even ~100 B per frame, 10 000 levels need ~5 MB, while thread-pool stacks are 1–1.5 MB. The result is a StackOverflowException. It cannot be caught, so the whole process dies for every organization, not just this team. Every later open of that page kills the restarted process again until someone repairs the data. The chain never reaches the JSON writer's MaxDepth guard: the mapping runs in the handler, before serialization.
- **Evidence:** BoardViews.cs:132-143 — `internal static IReadOnlyList<BacklogChildView> Of(...) => nodes.Select(node => { …; return new BacklogChildView(…, parents.Of(row), Of(node.Children, rows, parents)); }).ToList();` is called from BacklogRowView.Tree (line 110). - **Proposed fix:** Build the view tree without recursion, e.g. a post-order pass with an explicit stack that builds children lists before their parent record (or mutable builders frozen at the end), and add an endpoint test with a chain well past the stack threshold (e.g. 5 000 links) that asserts the process answers. - **Evidence:** BoardEndpoints.cs:107-120: `private const int MaxDepth = 1_024;` … "1 024 lets about five hundred through, beyond any hierarchy a team keeps". feat-027 spec.md:81 BR-T-4 "recursively, with no depth limit"; api-contract.md:50 "with no depth limit"; status.md Log: "the backlog answer is written with a JSON depth of 1 024".

- **Skeptic:** I confirmed it. The answer's JSON depth is about 3 + 2 per nested link: the response object, `items`, then a row object and its `children` array for each link. So in practice the client gets a 200 whose body is cut off and whose connection is aborted, rather than a clean 500. The page fails for every user of that team. BR-T-4 (spec.md:81) says «recursively, with no depth limit». api-contract.md:50 says the same, and BR-T-17 adds «the whole tree at full depth in one answer». feat-001 BR-H-2 sets no depth limit on writes. The fix belongs with C1's: either a written depth bound with its own refusal, or a stated read ceiling with a defined answer.

#### F-1 / FC1 — The test for a resend after a lost answer cannot fail: the first POST never reaches the recorder or the store, so a fresh requestId on retry would still pass

- **Where:** `src/frontend/src/features/boards/pages/BacklogPage.add.test.tsx:460`
- **Scenario:** Suppose AddChildRow made a new requestId on every Enter, for example after someone replaced `requestId.current ??= newRequestId()` with `= newRequestId()`. A retry after a lost answer would then send a different key. On the real server, where the first create did land, that creates a duplicate child, which is the case BR-T-10 and BR-M3-26 exist to prevent. This test would stay green. The override `server.use(http.post(WORK_ITEMS_URL, () => HttpResponse.error(), { once: true }))` answers the first POST before the in-memory API's handler runs, and that handler is the only place requests are recorded (`testApi.ts:693` `this.requests.push`) and items are created. No other Vitest or E2E test compares the requestIds of two attempts (E2E 26.3 at line 1124 only checks the type).
- **Evidence:** BacklogPage.add.test.tsx:462 short-circuits the first create with HttpResponse.error(). testApi.ts:686-697: `answer(...)` records into `this.requests` only when the in-memory handler runs.
