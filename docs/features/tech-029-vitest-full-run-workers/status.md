## Notes

Summary: Raise maxWorkers for a full Vitest run under the full-run lock and measure once; widened to every cheap lever on one full run.

### Profiling, 2026-10-13 (machine at 85–97% load from other sessions — numbers are upper bounds)

- Benchmark `--shard=1/6` (38 files, 437 tests): 6 min 56 s wall; 5 files take 725 of 896 file-seconds (`WorkItemFormPage` 283 s, `BacklogPage.mapping` 217 s, `WorkItemCard` 103 s, `BacklogPage.layout` 66 s, `AppLayout.organizations` 55 s); the nine `.test.ts` files take 1 s together; light files ~1.7 s each. So the node-project / lighter-setup / threads levers are worth seconds, not minutes.
- `WorkItemFormPage.test.tsx` alone, one worker: 153 s; a test that only mounts the shell and asserts once takes ~5 s. Full suite, baseline CPU split: tests 2130 s, setup 387, environment 398, collect 319 — startup is ~28% of CPU.
- CPU profile of one such test (worker thread): 8.4 s native — `internalModuleStat`, `package_json_reader`, `existsSync`, `lstat`: module loading from disk, once per file (each file is a fresh process); 4.9 s idle (timers, `findBy*` polling, MSW). Antimalware scanning of `node_modules` is the likely multiplier (the Task Manager showed it at 7% CPU / 7 MB/s).
- Not helping, measured: `defaultHidden: true` for Testing Library (4.76 s → 4.48 s, noise); `NODE_COMPILE_CACHE` (inconclusive under load: 19.6 / 24.2 / 13.2 s against 15.5 s without).
- Source imports are already deep (`@mui/material/Button`, per-icon paths); no barrel value imports to fix.

### Result: `isolate: false` works (2026-10-13)

What tech-028 could not do: one jsdom window and one module registry per worker, app modules re-evaluated per file.
- `src/test/sharedJsdom.ts` — a custom environment: one window per worker, the document emptied between files, globals left in place (a late callback must still find `MutationObserver`).
- `src/test/setup.ts` — `vi.resetModules()` before every file, so a `vi.mock` or a module-level store of one file is not seen by the next; node_modules packages (MUI, React, Testing Library) stay cached in Node, which is where the saving comes from. Hooks import app modules lazily so the test file and the hooks share one instance. After every test: `restoreAllMocks`, `unstubAllGlobals`, `unstubAllEnvs`.
- `testTimeout` 20 s → 60 s: the heavy page tests set 60–120 s with `vi.setConfig`, which did not reliably reach a worker that runs many files; they failed at 20 s under shuffle.
- Numbers, same machine, quiet, 4 workers: full suite 820 s (isolated) → 475 s; two `--sequence.shuffle` runs 3637/3637 green (801 s, 633 s; heavy files land late in a shuffled order). `maxWorkers=8`: 748 s and 0.9 GB free RAM — not worth it, stays 4. Antimalware exclusion changed nothing (836 → 820 s).

### Fast tier (2026-10-13)

- `src/test/slowFiles.json` (30 of 228 files, those whose tests add up to ≥ 15 s: 1673 s of 2061 s of test time), generated by `scripts/slow-files.mjs` from a Vitest JSON report; `npm run test:fast` (`scripts/test-fast.mjs`, sets `VITEST_FAST=1`) leaves them out. A speed hint, not a fence: `npm test` and verify.sh run everything; a heavy file missing from the list only makes the fast tier slower.
- Measured: `test:fast` 198 files / 2779 tests, 155 s wall; the full suite 475 s (was 820 s before the shared environment).
- `candidates.md`: per heavy file, the tests that are ≥ 5 s with ≤ 3 `expect`s — to fold or move down to a field's own component test. A list only; no test was edited.
- Not done on purpose: conventions for new page tests (one mount per scenario, assertions about a single field live in the field's component test) — a separate small change, to be agreed with the human.
