## Plan

<!-- S/M: implementation plan, 3-10 lines. L: see plan-backend.md / plan-frontend.md -->

Backend, two passes (D-9); no lanes — the write and the save share one domain decision and one lock sequence. Contract: [api-contract.md](api-contract.md).

- A1. **Storage: a `parent_id` column on `work_items`, not a link table.** One column holds one value, so BR-H-1's "one parent at most" is the schema's, and a replace is one UPDATE of one row — atomic with no window of two parents or none. The composite FK `(project_id, parent_id)` → `(project_id, id)` makes "same project" a database rule, `ck_work_items_parent_not_self` the self-link, and its index `(project_id, parent_id)` serves the children read. The other link kinds (release 2) take a table of their own then. Migration `AddWorkItemLinks` also creates `work_item_hierarchy_locks (project_id)`.
- A2. **Domain:** `WorkItem.ParentId`; `WorkItemHierarchy.Write` decides a write in the spec's order (deleted → `parent_changed` → self → level by rank → cycle with its path) and moves «Изменён» on the child and each live parent; `HierarchyTypes` is the process as the rules read it (level rank, Removed states); six `workitems.link.*` codes; `workitems.link.write` in `OrganizationPermissionCatalog`.
- A3. **Concurrency (ADR-0011, echelon 3):** every parent write of a project first locks its `work_item_hierarchy_locks` row `FOR UPDATE`, then the child `FOR UPDATE`, the old and new parents `FOR NO KEY UPDATE`, then walks the new parent's ancestry in one recursive CTE. Two writes for one child, or two that would close a cycle together, queue there and the second sees the first; a reorder's FK check (`FOR KEY SHARE`) is never waited on, so no deadlock.
- A4. **Slices:** `SetWorkItemParent` (`PUT …/workitems/{identifier}/parent`), `SaveWorkItem` gains `parent` (the same domain call, all or none), `GetParentCandidates` (`GET …/parent-candidates?text=&levelAbove=`); `WorkItem` gains `parent` and `children`.
- A5. **Tests:** domain units; an integration class per route, US-1/2/3/7 named, IDOR and anonymous cases, «Удалена» set by SQL (D-8), commit-gate races (stale write, cycle), the migration's rollback; catalog, permission and inventory tests.
- B1. **Backlog tree:** rows gain `parent` (live only) and `children` — the same team's backlog one level below, read through mod-006's membership and nested by `parent_id` in that backlog's StackRank order; the board untouched.
- B2. **Mapping** = A's `PUT …/parent` with the `levelAbove=true` search; US-4/5/7 integration tests, a 5 000-per-level tree volume test, the OpenAPI test of the WorkItems tag.

Frontend pass A (D-9): the form's section «Связанная работа», in mod-003's slice `features/workitems`; pass B writes its own lines.

- FA1. **API layer** `workitems/api`: `WorkItemRef` (§ 2.1); `WorkItem` gains `parent` and `children` (§ 2.2); `SaveWorkItemBody.parent` is a `ParentChange` (§ 2.3); `getParentCandidates(org, project, identifier, text, { levelAbove })` (§ 3.4 — the form never sends `levelAbove`); key `['workitems', 'parentCandidates', org, project, identifier, levelAbove, text]`; hooks `useParentCandidates` and `useRefreshWorkItem` (the read again after `parent_changed`). The six `link*` constants stay as backend A named them.
- FA2. **Logic** `workitems/lib`: the draft gains `parent`; `changesOf` sends `{ parentId, seenParentId }` only when the chosen id differs from the loaded one; `rebaseDraft` lays the touched fields over a fresh read; `parentOptions` («Нет родителя» first, then the hints, as `assigneeOptions`); `allowedParentTypes` from the process read's level ranks for the helper; `placeRefusal` lands the six `workitems.link.*` codes on «Родитель».
- FA3. **Components**, MUI core: `ParentPicker` (`Autocomplete`, debounced search from an empty text, the type icon as its start adornment, the value's state beside it, an `OpenInNew` `IconButton` linking the stored parent), `ChildrenList` (`List` with `TypeMark`, the identifier as a `Link`, `StateName`), `RelatedWorkSection` (the `h2` «Связанная работа» below «Описание»); while the form loads, `FormSkeleton` covers the section.
- FA4. **State**: server state in TanStack Query — the item's entry updated by the save's answer and by the re-read; the draft in the form's `useState`, as mod-003.
- FA5. **Tests**: units on the draft, the options, the allowed types and the refusal mapping; component tests per US-1 / US-3 scenario and US-2's form refusals on the in-memory API (`testApi.ts` gains `parent`/`children`, the PATCH's `parent` with § 3.2's checks in order, the candidates route).
