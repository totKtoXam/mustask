# ADR-0045: Keep images as bytes in a PostgreSQL schema of their own, check them with our own header reader before libvips decodes them, and sweep unbound uploads hourly

- Status: accepted (by the human in chat, at feat-078 gate-2, 2026-11-17: D-1 A NetVips, D-2 A, D-3 A; licences still verified against the pinned versions' licence files)
- Date: 2026-11-17
- Context: `feat-078-description-images`, stage 03 (design): [spec](../features/feat-078-description-images/spec.md) D-1..D-10, BR-IM-3, -4, -6, -8, -10, -11, -16, -17, -19, -20, § Non-functional requirements; [review](../features/feat-078-description-images/review.md) R-13. Builds on ADR-0002 (explicit migrations), ADR-0009 (EF Core), ADR-0011 (pessimistic locks), ADR-0029 (the item's read and write rules), ADR-0030 rule 7 (data leaves with the purge) and ADR-0039 (the stored description, which gains the image element). feat-059 builds on this ADR and takes no number of its own for it (its ADR-0041 decision 6 (c) "stores through feat-078's storage"). Only the human sets `accepted`; the spec (BR-IM-17) requires that before code.

## Problem

Описание gets images. The human decided where the bytes live (D-1: in the database, in a schema of their own) and that large images are compressed without visible loss (D-2, D-8). Four things follow that the repository has none of: a store for binary data, a dependency that decodes and encodes images (and so parses hostile files), a background job that deletes data on a clock, and an upload model a second feature (feat-059) must reuse without changing it. Each has long-term consequences: the store and its identifier are expensive to change once descriptions reference them, the image library is a native or licensed dependency at a security boundary, and the sweep is the first job that removes user data by time (mod-005 BR-DR-5's "no clock" guard, `RetentionTests`, lists every hosted service).

## Options considered

### A. Where and how the bytes are kept (D-1 fixes "the database, own schema")

- **A1: `bytea` in a table of the images schema, one `MustaskDbContext`, one migration history.** One connection, one transaction for a description write and its binds, the purge's cascade works across schemas, ADR-0002's single migration step stays single. Chosen.
- **A2: PostgreSQL large objects (`lo`).** Streamable by offset, but outside foreign keys and cascades (orphans need `vacuumlo`), outside row locks, with their own permissions. The bind/sweep rule and the purge would each need custom code. Rejected.
- **A3: a second `DbContext` for the images schema.** A clean module wall, but two migration histories and two bundles in the deploy, and a description write plus its binds then spans two contexts (a shared connection and transaction by hand). The wall is had more cheaply by the model test in decision 1. Rejected.
- **A4: a separate database role owning the images schema.** Defence in depth, but a second connection string and pool, and the bind could no longer share the description write's transaction. Not now.

### B. The image library (BR-IM-2..-4, -20)

What the library must do is narrower than it first looks, because two jobs are better done by our own code (decision 2): recognising the format and reading dimensions and frame counts from the header, and removing metadata at the container level (US-2 requires a small JPEG's pixels not be re-encoded, which no library's "strip" does without re-encoding, and an animated image is never re-encoded: BR-IM-4 (6)). The library decodes still PNG, JPEG, GIF and WebP within a memory cap, applies orientation, scales, keeps or carries the ICC profile, and encodes JPEG and WebP at a chosen quality, PNG and WebP losslessly, and a still GIF (BR-IM-4 (2) and BR-IM-20 scale a GIF too). SSIM is ours as well (decision 2): it is twenty lines over two luminance planes and must match the spec's definition exactly, which no library's metric is promised to.

## Decision

**A1, and NetVips (libvips) as the image library, behind our own header reader, metadata stripper and SSIM.** If the human prefers a fully managed dependency and the company holds or buys a Six Labors commercial licence, ImageSharp 3.x replaces NetVips behind the same port with no other change to this ADR (decision 2).

### 1. The store: an images module owning the `images` schema

- **Module.** A module `Images` in the usual four places (`Mustask.Domain/Images`, `Mustask.Application/Features/Images`, `Mustask.Infrastructure/Images`, `Mustask.Api/Features/Images`). It alone owns the schema `images`: its entities map with `ToTable(..., schema: "images")`, nothing else does, and a model test over `MustaskDbContext` (the family of the `Code` unique-index test) pins both directions. Other modules reach it only through the ports of decision 4.
- **Tables.** `images.images`, one row per image: `id`, `purpose` (string-stored enum), `format` (png, jpeg, gif, webp), `byte_length`, `width`, `height`, `frame_count`, `uploaded_by` (the Keycloak subject, as `created_by` elsewhere), `uploaded_at`, `bound_at` (null while unbound), `work_item_id`; and `images.image_contents` (`image_id` primary key and a cascading key to `images.images`, `content bytea`). The split keeps a tracked load of an image (the bind) and every metadata query (the sweep, the reference check) from ever touching the bytes. `content` gets `SET STORAGE EXTERNAL`: the four formats are already compressed, so TOAST stores the bytes out of line without spending CPU on compressing them again.
- **The work item reference.** For the description purpose `work_item_id` is the item the upload was made for (BR-IM-5), and stays the item it is bound to (BR-IM-8 binds only to that item). It is a cross-schema foreign key to `work_items` with `ON DELETE CASCADE`: ADR-0030 rule 7's default, so a purge removes the item's images, bound, unbound, referenced or not, in the purge's own transaction (BR-IM-16), and `WorkItemReferenceInventoryTests` classifies it as cascading. A check constraint ties the owner columns to the purpose: today, description ⇒ `work_item_id` set.
- **The identifier.** `id` is a random version-4 uuid (`Guid.NewGuid()`), the one place the project departs from its version-7 ids: the id is the address readers hold (BR-IM-10), and a version-7 id would date the upload. 122 random bits make it unguessable; it carries no organization, project, item or user. The stored description holds this id only (the element's exact markup is the plan's and `api-contract.md`'s, under ADR-0039's reduction); the address a page loads is derived by the surface (BR-IM-7, -19).
- **Immutability.** A row's bytes never change after insert (spec § Operation completeness); `bound_at` and nothing else is ever updated. The `xmin` convention (ADR-0010) applies but is not relied on: concurrency is decision 3's locks.
- **Migrations.** In the one migration stream, applied by the explicit step (ADR-0002). The first creates the schema (`EnsureSchema`), both tables and the key, and drops all of it in `Down`. `__EFMigrationsHistory` stays where it is.
- **Reads.** The read route (US-4) decides access first, then reads the content in one query with sequential access into a pooled buffer of the known length (at most 5 MB), returns the connection to the pool, and only then writes the response: a slow client never holds a database connection. Reads decode nothing and take no part in decision 5. The panel cannot put its bearer token on an `<img>` (ADR-0022: the token lives in page memory, the session cookie is limited to `/api/session`), so the panel fetches the bytes with the token and shows them through an object address; that is the frontend plan's, and it is why BR-IM-19's host-supplied address resolver exists.
- **Response headers.** `Content-Type` of the stored format; `X-Content-Type-Options: nosniff`; `Content-Security-Policy: default-src 'none'; sandbox` and `Cross-Origin-Resource-Policy: same-origin`, so a polyglot opened directly runs nothing; `Cache-Control: private, no-cache` with `ETag` set from the id. `private` keeps every shared cache out (BR-IM-11); `no-cache` lets the browser keep the bytes but makes it ask again, so every display passes the live access check (BR-IM-11: "a revoked right stops the next read") and a repeat costs a `304` without a body. Every refusal (no right, unbound and not the caller's, swept, purged, made up, malformed id) is the same `404` with the same body (BR-IM-11, NFR Non-disclosure).

### 2. Processing: our header reader first, then libvips under caps

Every path (upload, reduction, feat-059's upload) runs one intake, a port `IImageIntake` in `Mustask.Application/Abstractions/Images` implemented in `Mustask.Infrastructure/Images`, in this order:

1. **Size,** against the route's cap (5 MB, or 20 MB for a reduction: BR-IM-3 (b)), enforced on the request body limit of the route and while reading, never from the declared length alone.
2. **Our header reader, managed code, no library.** Recognises the format from magic bytes only (BR-IM-2). Walks the container without decoding pixel data: PNG chunks (IHDR, and acTL, which marks an animated PNG), JPEG markers up to the frame header, GIF blocks (skipping image data sub-blocks unread) and WebP RIFF chunks (VP8, VP8L, VP8X, ANIM, ANMF). From that it takes the dimensions, the frame count, the summed pixels of all frames, whether a WebP is lossless, and the orientation; and it refuses anything outside BR-IM-3 (c) or structurally broken (a truncated container) before a byte reaches libvips. This is the decode cap that does not depend on a library's honesty about its own limits, and it is what makes the 40 KB bomb of US-2 "refused, not decoded".
3. **Our container stripper, managed code.** Rewrites the file without its metadata chunks and segments: EXIF, XMP, IPTC, comments, thumbnails, text chunks. It keeps the ICC profile, PNG's colour chunks and GIF's loop extension, and writes back one minimal EXIF holding only the orientation where the pixels are not re-encoded (BR-IM-4 (1)). An animated image ends here (BR-IM-4 (6)); so does a still image that BR-IM-4 does not re-encode (a JPEG up to 1 MB, a PNG within 16 MP). Its output is pixel-identical to the input by construction.
4. **libvips, only for the re-encode path,** inside decision 5's gate: a per-format loader called by name (never a "load anything" call), the untrusted-input block switched on, the operation cache off; orientation applied, scaled to 16 777 216 pixels (BR-IM-4 (2)), encoded with only the ICC profile kept. For a lossy JPEG or WebP over 1 MB: a bounded search over the encoding quality for the smallest result with SSIM ≥ 0.98 (BR-IM-4 (4)); for a reduction, quality down to SSIM 0.95, then scaling down to half the sides (BR-IM-20 (2)). PNG and lossless WebP are encoded losslessly. Then BR-IM-4 (5): the stored image is never larger than the upload.
5. **SSIM, ours.** On luminance, 8×8 windows, the constants of the method's published definition; both pictures decoded by libvips to the same size and colour space. The test suite pins it against hand-computed values, so a library change cannot move it.

The profile is carried, never converted: the encoded result keeps the source's ICC profile, so the SSIM compares like with like and colours stay as uploaded (BR-IM-4 (1) allows either).

### 3. The hourly sweep, and why a bind and the sweep never interleave

- **Where it runs.** A `BackgroundService` in the API process, registered as a singleton and as a hosted service, as `RealmReadinessMonitor` is, so tests call its one-run method directly with a controlled clock. It runs once at start, then every hour on a `PeriodicTimer` over the injected `TimeProvider`; the cutoff is `IClock.UtcNow − 2 h`, and `uploaded_at` comes from the same `IClock`. An upload is therefore never removed before 2 h, and, while the server runs, removed at the first run after that, at most 1 h later: within 3 h (BR-IM-16). Missed runs while the server is down are made up by the start-up run.
- **What it does.** Deletes unbound rows of every purpose with `uploaded_at <= cutoff` (BR-IM-19, US-5's last scenario), in batches selected `FOR UPDATE` in id order, each batch its own short transaction; the contents go by the cascading key. One log line per run with the count only (US-5).
- **The race rule (ADR-0011).** The description write, inside its own transaction and after locking the item as it does today, locks the referenced image rows `FOR UPDATE` in id order, checks each against BR-IM-8 on what it read under the lock (exists, `work_item_id` is this item, and bound or uploaded by the writer), sets `bound_at` on the unbound ones, then stores the description. The sweep takes only image rows, in the same order, so the two can wait on each other but cannot deadlock. If the sweep locked first, the write finds the row gone and refuses (the whole write, BR-IM-8). If the write locked first and commits, the sweep's `DELETE ... WHERE bound_at IS NULL` re-checks the committed row and skips it. If the write rolls back, the row is unbound and the sweep removes it. No stored description can reference a removed image.
- **Options not taken.** `pg_cron` (an extension on the VM and in the Aspire container, and the rule split away from the code); Quartz or Hangfire (a dependency for one hourly job); sweeping lazily on the next upload (an idle instance never sweeps, so the 3-hour bound fails). Several API processes need no leader: the sweep is idempotent under the locks.
- `RetentionTests`' list of hosted services gains the sweep with its reason: it deletes unbound image uploads and writes no work item row.

### 4. The seam for feat-059

- **The purpose slot.** `ImagePurpose` is a domain enum stored as a string; this task ships `WorkItemDescription`. feat-059 adds `FeedbackSubmission` with its own owner column (or columns) in the `images` schema, in its own migration, extending decision 1's purpose check constraint, and no change to anything else here.
- **Purpose-agnostic parts,** shipped here and used unchanged by feat-059: the store, `IImageIntake` (all of decision 2, the reduction included), decision 5's gate, the identifier and response headers of decision 1, and the sweep of decision 3 over every purpose.
- **Per-purpose parts,** each the owning slice's: who may upload (this task: the item's description edit rule, BR-IM-5; feat-059: its sender, ADR-0041 decision 6), what the upload is made for, which write binds it (this task: the description write, through a port `IImageBinding` that locks in id order, checks a purpose-supplied rule and binds; feat-059: send and edit of its report, through the same port with its own rule), and who reads it. This task's read route serves an image bound to a work item to that item's readers, whatever its purpose, and an unbound one to its uploader; feat-059's own operation adds the sender as a reader of their report's images (BR-IM-11, -19).
- feat-059 needs no ADR beyond its ADR-0041 and this one. If it needs a rule here changed, the change is an amendment of this ADR while it is proposed, or a new ADR once it is accepted.

### 5. A bound on concurrent decodes (R-13)

- Decision 2 steps 4 and 5, everything that decodes pixels, run inside one process-wide concurrency limiter (`System.Threading.RateLimiting`, as `AggregateReadLimiter` does): a few permits, a short queue and a bounded wait. Past them the upload or reduction is refused with `503`, `Retry-After`, and its own error code and Russian text, added by the backend stage (ADR-0005). The permits, the queue and the wait are configuration, tuned on the stand, not constants (backend.md § Named values, 1); the plan states the defaults with the memory arithmetic for a 60 MP still and a 48 MP reduction.
- libvips' own worker-thread count and memory are capped process-wide at start, so the limiter's arithmetic holds.
- Steps 1-3 decode nothing and run outside the gate; the request bodies waiting for it are bounded by the route's size cap times the permits plus the queue.

**Implementation note (feat-078 stage 4a, 2026-11-17).** Decision 3's sweep
must not wait on id-ordered row locks: a purge's cascade deletes image rows in
no fixed order, so a waiting sweep batch could deadlock with it. The sweep
deletes in batches with `SKIP LOCKED`, then handles the skipped rows one per
transaction, waiting for each. The bind/sweep outcomes and the 3-hour bound
are unchanged ([plan-backend.md](../features/feat-078-description-images/plan-backend.md)).

## Consequences

- **Database size and backups.** Images will soon be most of the database. An estimate, not a measurement: 100 active members inserting 5 images a week at about 300 KB stored (a typical PNG screenshot) is ~150 MB a week, ~8 GB a year; scale it linearly by the real figures. Bound images are never collected while their item lives (D-9), so the volume only grows with edits. The bytes are already compressed, so a dump's compression gains nothing on them, and dump and restore times grow linearly. A schema of its own lets an operator dump `images` on its own schedule (`pg_dump -n images`), at the price of a restore where descriptions may reference images newer than the images dump. `docs/deploy/vm.md` describes no backup today; the volume and the schedule go to the operator through it.
- **Deletes.** The sweep and the purge leave space that autovacuum makes reusable but does not return to the disk; acceptable at these volumes.
- **A native dependency.** NetVips brings a native package per OS: the VM's Linux build is confirmed by the deploy runbook's check, and the developers' Windows build by CI. libvips' LGPL obligations are those of a dynamically linked library (to be confirmed, see Options B). A libvips security fix means a package bump with the hostile corpus green, the same rule as AngleSharp's.
- **Our own parsers.** The header reader and the stripper are a security boundary we own, like ADR-0039's reducer: iterative walkers, deterministic bounds, the hostile corpus a permanent test input. In exchange the library sees only well-formed, capped, still images, and can be replaced behind `IImageIntake`.
- **Simpler:** one transaction for a description and its binds; the purge needs no step; feat-059 adds a purpose, not a mechanism.
- **Harder:** the API process now holds request bodies and decoded pixels; the gate makes uploads wait or refuse under load. Every unbound upload costs storage for up to 3 h, unbounded per user (spec R-14, accepted risk).
- **Locked in:** the id format of stored references, and bytes in the database. Moving them to object storage later is a copy job plus a new read path, not a description migration, because descriptions hold ids, not addresses.
- **Revisit when:** the images schema passes a size the operator cannot back up in the night window; quotas or rate limits are asked for; or images reach other fields or comments (feat-018's later lines).

- [x] **D-1 The image library.** (A, recommended) NetVips: free to use as the agent understands its licences (to verify), lowest memory and fastest, the only option besides ImageSharp and Magick.NET that encodes GIF; a native package to deploy. (B) ImageSharp 3.x: fully managed, memory-safe decoders, nothing native, but under the Six Labors Split License a closed internal tool of a company above its revenue threshold likely needs a paid commercial licence: choose it only if the company holds or buys one. (C) SkiaSharp: MIT, but it cannot encode GIF, so a still GIF over 16 MP or 5 MB could only be refused. (D) Magick.NET: every format, at the largest attack surface and memory use; not recommended for a parser of hostile files.
- [x] **D-2 An animated PNG.** The spec names animated GIF and WebP only. (A, recommended) Treat an animated PNG like them (D-10): every frame kept, only metadata removed, the same frame caps, refused over 5 MB. (B) Store its first frame only, as a still PNG: smaller, but the member sees an animation turn still without being told.
- [x] **D-3 Scaling a still GIF** (BR-IM-4 (2), BR-IM-20). A scaled picture has colours a GIF palette may not hold, so "stored pixels equal the scaled ones" cannot hold exactly. (A, recommended) Scale a GIF by nearest neighbour, which keeps the original palette and so stays exact to what was scaled, at a jaggier look. (B) Scale smoothly and re-quantise to 256 colours: smoother, but a lossy step BR-IM-4 (3) excludes.
- [ ] **D-4 Backups.** Not an architectural choice, but owed: who sets the backup schedule for the VM's database now that images will dominate it, and whether `images` is dumped on its own schedule (Consequences).
